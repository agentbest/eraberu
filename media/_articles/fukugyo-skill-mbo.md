「目標管理を入れたい」という依頼で、目標のシートを作って配り、期初に書かせ、期末に見ると、目標は期初に書いたきり誰も見ておらず、期末に「達成したことにする」か「忘れていた」かのどちらかになります。目標管理は、シートではなく、「目標をどう起こし、途中でどう見て、期末に評価とどう分けて振り返るか」の設計です。結論を先に書くと、**目標管理の設計は、目標の起こし方・数と粒度・途中の確認・振り返りと評価の関係の四つで組み、目標は等級の期待と部門の方針から本人が起こし、数は三つまでで結果と行動を分け、数字の目標は全部にしない、途中の確認は月次で進み・障害・変更の三つだけ、振り返りは評価の面談の材料であって評価そのものではなく、水準は担当者が決めず、運用の負担を最小にします。**評価の設計は[評価制度を設計する](/media/fukugyo-skill-hyouka/)に、等級は[等級制度を設計する](/media/fukugyo-skill-grade/)に、三つのつながりは[人事制度を設計する](/media/fukugyo-skill-jinji-seido/)に書いています。ここでは、目標管理の型に絞ります。

## 「シートを配る」だけで形だけになる

| 配るだけの形 | 何が起きるか |
|---|---|
| 期初に書いて、期末まで見ない | 忘れられる。期末に「達成したことにする」 |
| 目標が十個 | 全部が薄く、どれも追えない |
| 全部を数字に | 数字にならない仕事（育成、調整）が無視される |
| 目標の達成率で評価が決まる | 低い目標を書く。挑戦しなくなる |
| 上司が目標を書いて渡す | 本人のものにならない |
| 途中で状況が変わっても変えられない | 期末に「前提が変わったので無効」になる |

目標管理が機能するのは、「途中で見る」と「評価と分ける」の二つが設計されているときです。この二つが無いシートは、配らないほうが負担が少ない。

## 設計の四つ

| 決めること | 中身 |
|---|---|
| 目標の起こし方 | 等級の期待（この段階に期待すること）と部門の方針から、本人が起こす。上司は確認と修正 |
| 数と粒度 | 三つまで。「結果の目標」と「行動の目標」を分ける。期の終わりに「できたか」が事実で分かる粒度 |
| 途中の確認 | 月次で、目標ごとに「進み・障害・変更」の三つだけ。短く |
| 振り返りと評価の関係 | 期末の振り返りは、評価の面談で「事実」を語る材料。達成率を評価の点数にしない |

四つを一枚にして、依頼側と合意します。シートの形は、四つが決まってから作ります。

### エラベルの見解

担当する側から見ると、目標管理の設計で最も差がつくのは、「目標の達成率を、評価の点数にしない」を依頼側に通せるかです。受ける側は、依頼側の「目標管理を評価に使いたい」に応え、達成率を点数にします。すると、社員は達成できる低い目標を書き、上司は目標の水準を巡って交渉し、目標管理が「点数を決めるための駆け引き」になります。目標は「この期に何に取り組むか」を本人と上司で合わせるもので、期末の振り返りは「事実を語る材料」として評価の面談に持ち込む。評価は、等級の期待に照らした観点と行動の言葉で行う。この分け方があると、社員は挑戦する目標を書けます。エラベルで担当者を選ぶ企業には、「目標の達成率が、そのまま評価の点数になっていませんか」を、私たちから先に聞いています。受ける側がその場で使える判断としては、目標のシートに「達成率」の欄を作らないこと。「期末の事実」の欄だけを置きます。

## 目標の起こし方

| 順 | 中身 | 誰が |
|---|---|---|
| 一 | 部門の方針を、期初に一枚で共有。「この期に部門として何を目指すか」 | 部門の責任者 |
| 二 | 本人の等級の期待（この段階に期待すること）を確認 | 本人と上司 |
| 三 | 方針と期待から、本人が目標の案を三つまで書く | 本人 |
| 四 | 上司と確認。「期末に、できたかどうかが事実で分かるか」「等級の期待と合っているか」で修正 | 本人と上司 |
| 五 | 確定。途中の確認の日を決める | 上司 |

目標の水準（どのくらいを目指すか）は、本人と上司が決めます。担当者は、起こし方の順と、確認の問いを作るまでで、個人の目標の水準に関わりません。部門の方針が無い会社では、方針の一枚を先に作ることを依頼側に提案します。

## 数と粒度：結果と行動を分ける

| 種類 | 中身 | 例の形 |
|---|---|---|
| 結果の目標 | 期末にどうなっているか。数字になるものは数字で。一つか二つ | 「〇〇の案件を、〇〇の状態まで」「担当の〇〇を、〇件」 |
| 行動の目標 | 期の中で、どう動くか。等級の期待の「行動の言葉」に対応 | 「〇〇の場面で、自分で判断して進める」「後輩の〇〇を、週に一度確認する」 |

全部を数字にすると、数字にならない役割が消えます。全部を行動にすると、結果が見えません。結果を一つか二つ、行動を一つか二つ、合わせて三つまでです。粒度は「期末に、できたかどうかが事実で分かるか」で確かめます。「頑張る」「意識する」は事実で分からないので、目標になりません。

## 途中の確認：月次で三つだけ

| 確認すること | 中身 |
|---|---|
| 進み | 目標ごとに、いまどこか。一言 |
| 障害 | 進まないなら、何が邪魔しているか。上司が取り除けるものか |
| 変更 | 前提が変わったなら、目標を変えるか。変えるなら記録に残す |

月次の確認は、1on1の中で行うと、負担が増えません。1on1の型は[1on1・メンタリングの副業の実務](/media/fukugyo-one-on-one-shigoto/)に書いています。途中で目標を変えることを認めないと、期末に「前提が変わった」で無効になります。変更は記録に残し、期末の振り返りで「なぜ変えたか」も事実として語れる形にします。

### エラベルの見解

相談で最も多い思い込みは、受ける側の「目標管理は、全社員に同じシートで同時に入れるもの」というものです。実際には、部門の方針が一枚になっていて、上司が月次の確認を回せる部門から始めないと、シートだけが配られて形だけになります。一つの部門で一期回し、「途中の確認が回ったか」「期末の振り返りが評価の面談の材料になったか」を見てから、次の部門に広げる。運用が回ることが、シートの形より大事です。受ける側がその場で使える判断としては、導入の一枚に「最初に回す部門」を一つだけ書き、全社への展開は「一期回した結果を見て」と依頼側と合意しておくこと。

## 振り返りと評価の関係

| 場 | 中身 | 関係 |
|---|---|---|
| 期末の振り返り | 目標ごとに、期末の事実（何がどうなったか、何をしたか）を本人が書く。変更した目標は、変更の理由も | 評価の面談の「本人が場面を話す」段の材料 |
| 評価の面談 | 等級の期待に照らした観点ごとに、事実と判断 | 振り返りの事実を、観点に照らす。達成率を点数にしない |
| 処遇への接続 | 評価の判断が処遇に対応 | 目標の達成率は直接には接続しない |

目標の達成率を評価の点数にすると、目標の水準の駆け引きが始まります。目標は「取り組むことを合わせる仕組み」、評価は「期待に照らして判断する仕組み」、と分けます。処遇への接続と法令上の整理は、依頼側と専門家の確認に従います。個別の判断は専門家にご確認ください。

## 運用の負担を最小に

| 負担を増やすもの | 減らす |
|---|---|
| 目標が多い | 三つまで |
| シートの欄が多い | 目標・結果か行動か・期末に分かる形か・月次の三つ・期末の事実。それだけ |
| 途中の確認が別の会議 | 1on1の中で |
| 全社で同時に | 一部門から |
| 上司が目標を書く | 本人が書き、上司は確認の問いで |

負担が大きい仕組みは、二期目に消えます。一枚で説明でき、月次の確認が数分で済む形にします。

## よく起きる詰まりと直し方

| 詰まり | 直し方 |
|---|---|
| 目標が十個並ぶ | 三つまでに。結果と行動を分けて選ぶ |
| 全部が数字 | 行動の目標を一つ足す。数字にならない役割を確かめる |
| 達成率で評価したい | 分ける理由（低い目標を書く構造）を伝える。判断は依頼側 |
| 途中の確認が無い | 1on1の中に月次の三つを置く |
| 上司が目標を書いている | 本人が書き、上司は確認の問いで。問いを一枚に |
| 部門の方針が無い | 方針の一枚を先に。無ければ目標は起こせない |

## まとめ

- シートを配るだけでは形だけ。**途中で見る・評価と分ける**の二つが設計の要
- 四つは**起こし方・数と粒度・途中の確認・振り返りと評価の関係**
- 目標は**等級の期待と部門の方針から本人が起こす**。水準は本人と上司。担当者は関わらない
- **三つまで。結果と行動を分ける。全部を数字にしない**。期末に事実で分かる粒度
- 途中の確認は**月次で進み・障害・変更の三つ**。1on1の中で。変更は記録に
- 振り返りは**評価の面談の材料**。**達成率を点数にしない**。処遇への接続は依頼側と専門家
- **一部門から**。運用が回ってから広げる。負担を最小に

## よくある質問

### 依頼側から「OKRのような仕組みを入れたい」と言われました

仕組みの名前が何であれ、設計の四つ（起こし方・数と粒度・途中の確認・振り返りと評価の関係）は同じです。名前の付いた仕組みを持ち込むと、その仕組みの型に依頼側を合わせることになり、運用で崩れます。「御社の等級の期待と部門の方針から起こし、途中で見て、評価と分ける形を作ります。名前は御社で決めてください」と、構造で答えます。名前の付いた仕組みの詳細を担当者が断定することもしません。

### 営業部門から「数字の目標だけでよい」と言われました

結果の目標が数字になるのは自然ですが、行動の目標を一つ足すことを勧めます。数字だけだと、数字に出ない動き（新人の同行、他部門との調整、記録の整備）が目標から消え、その動きをしている人が評価されません。「結果は数字で、行動を一つ」の形にすれば、営業部門でも等級の期待（人を通して回す、など）と目標がつながります。決めるのは部門の責任者です。

### 期の途中で、会社の方針が大きく変わりました

目標の変更を認め、記録に残す設計にしておけば、対応できます。部門の方針の一枚を更新し、各自の目標を月次の確認の「変更」で見直します。変更した目標は、期末の振り返りで「なぜ変えたか」と「変えた後の事実」を語る形にします。変更を認めない設計だと、期末に目標の全部が無効になり、目標管理そのものが信用されなくなります。
