案件が決まり、依頼側から「うちはこのATSとこのチャットを使っています」と言われた。自分が使い慣れたツールではなく、覚えるのに時間がかかりそうで、自分のツールで作業して結果だけ渡す形にできないかと考える。結論を先に書くと、**人事の副業では、依頼側のツールに合わせるのが基本です。候補者の情報は依頼側の仕組みの中で扱うものなので、自分のツールに持ち出して作業する形は、依頼側の情報管理から見て避けたい形になります。合わせるときは、「触ってよい範囲」「通知の設定」「自分の記録の置き場」の三つを最初に決めておけば、慣れないツールでも迷いません。**依頼側のツールが使いにくいと感じても、変えることを求めるのではなく、自分の作業の順番を変えて対応します。自分のツールをどこまで持ち込むかの判断は[ツールを統一するか合わせるか](/media/fukugyo-tool-toitsu/)に、ツールの揃え方は[使うツールをそろえる](/media/fukugyo-tool/)に、アカウントの管理は[アカウント管理のしかた](/media/fukugyo-account-kanri/)にまとめています。

## 依頼側のツールに合わせる理由

自分のツールのほうが速くても、依頼側のツールに合わせるのには理由があります。

| 理由 | 内容 |
|---|---|
| 候補者の情報が依頼側の管理下に留まる | ATSの中で候補者を扱えば、情報は依頼側の仕組みから出ない。自分のツールに写せば、依頼側の外に情報が出る。[個人情報の扱い](/media/fukugyo-kojin-jouhou/) |
| 依頼側の社内の人と同じものを見られる | 担当者や面接官が見ている画面と同じものを見て話せる。自分だけ別のツールだと、状況の認識がずれる |
| 記録が依頼側に残る | 自分の操作の記録が依頼側の仕組みに残り、担当者が替わっても引き継げる。自分のツールの記録は依頼側に残らない |
| 案件の終了時に返すものが少ない | 依頼側の仕組みの中で完結していれば、終了時にアカウントの停止だけで済む。自分のツールに情報があると、消す作業と確認が要る |
| 依頼側の情報管理の決まりに沿える | 依頼側が「情報はこの仕組みの中で」と決めていれば、それに沿うことが契約の前提になる |

理由の要点は、「候補者の情報が依頼側の管理下に留まる」ことです。自分のツールで作業する形は、速く見えても、候補者の情報を依頼側の外に出すことになり、依頼側の情報管理から見れば、担当者の端末やクラウドに情報が散らばる形です。依頼側のツールの中で作業すれば、情報は出ず、終了時の整理も軽くなります。

## 最初に決める三つのこと

依頼側のツールを使い始める前に、三つを担当者と決めておきます。

| 決めること | 内容 | 決めないとどうなるか |
|---|---|---|
| 触ってよい範囲 | ATSのどの画面を見てよいか、どの項目を編集してよいか、候補者の状態を自分で変えてよいか、削除は誰がするか | 自分の範囲外の情報を見たり、依頼側の社内の人が管理している項目を変えたりして、後で指摘される |
| 通知の設定 | チャットの通知をどこまで受けるか、ATSの通知をメールで受けるか、副業の時間外に通知が来ることをどう扱うか | 本業の時間中に副業の通知が来て、対応するかで迷う。通知を全部切って、依頼側からの連絡に気づかない |
| 自分の記録の置き場 | 稼働ログ、判断のメモ、自分の側の議事録を、依頼側のツールの中に置くか、自分の副業用のツールに置くか | 自分の記録が依頼側のツールに残り、終了時に持ち出せない。逆に依頼側の情報を自分の記録に書いてしまう |

三つの要点は、「触ってよい範囲」を項目の単位で決めることです。「ATSを使ってください」だけでは、自分の範囲がどこまでかが分かりません。候補者の状態を「一次面接に進む」に変えるのは自分か担当者か、評価の欄に書くのは誰か、候補者の連絡先を変更してよいか。項目ごとに決めておくと、依頼側の社内の人の作業と重ならず、自分の操作の範囲も記録で示せます。権限の範囲の考え方は[権限がないと動けない場面](/media/fukugyo-kengen-nai/)に、権限の確認は[パスワードの受け渡し](/media/fukugyo-password/)に書いています。

### エラベルの見解

相談で最も多い思い込みは、「依頼側のツールを知らないと、案件を受けられない」というものです。実際には、依頼側の担当者は、外部の担当者がそのツールを使ったことがあるかどうかより、候補者の対応やスカウトの進め方の経験を見ています。ツールは、案件の最初の数日で覚えられるもので、依頼側もそれを分かっています。ATSの種類が違っても、候補者の状態を進める、記録を残す、連絡を送る、という操作の骨格は同じです。

見ていて差がつくのは、ツールの経験ではなく、最初に「触ってよい範囲」を聞いているかです。聞いている人は、慣れないツールでも自分の範囲だけを触るので、依頼側の社内の作業を壊しません。聞いていない人は、慣れたツールでも、依頼側の社内の人が管理している項目を善意で直してしまい、指摘を受けます。エラベルでは、依頼側との契約の際に、担当者が触る範囲をツールの項目の単位で確認する形を取っています。ツールの経験の有無を登録の条件にはしていません。

## 初めてのツールの覚え方

初めて使うATSやチャットは、全部を覚えようとせず、自分の範囲の操作だけを覚えます。

| 手順 | 内容 |
|---|---|
| 一、自分の範囲の操作を書き出す | 候補者の検索、状態の変更、連絡の送信、記録の入力、のように、自分が触る操作を列挙する |
| 二、担当者に一度見せてもらう | 画面を共有してもらい、自分の範囲の操作を一通り見る。全部の機能の説明は要らない |
| 三、依頼側の使い方の癖を聞く | 「状態の名前はこう使っている」「この欄は面接官が書く」のように、依頼側の社内での使い方を聞く。ツールの機能より、この癖のほうが大切 |
| 四、最初の数件を担当者に確認してもらう | 自分が入力した最初の数件を担当者に見てもらい、依頼側の使い方と合っているかを確認する |
| 五、自分用の手順を一枚にする | 自分の範囲の操作と依頼側の癖を、一枚のメモにする。依頼側の情報は書かず、操作の順番だけ |
| 六、分からない操作は触らない | 自分の範囲外の操作や、影響が分からない操作は、担当者に聞くまで触らない |

覚え方の要点は、「三」の依頼側の使い方の癖を聞くことです。同じATSでも、会社によって状態の名前の使い方や、どの欄を誰が書くかが違います。ツールの説明書には書かれていない、その会社の運用を聞いておくと、慣れたツールでも慣れないツールでも、依頼側の社内の人と同じ使い方ができます。初回の打ち合わせで聞く項目は[初回打ち合わせの進め方](/media/fukugyo-shodan/)に整理しています。

## 依頼側の社内の使い方に合わせる線

依頼側のツールを使うとき、ツールの機能ではなく、依頼側の社内の運用に合わせる場面があります。

| 場面 | 合わせ方 |
|---|---|
| 状態の名前の使い方 | 依頼側が「書類選考中」をどの時点で使うかに合わせる。自分の解釈で変えない |
| 記録の書き方 | 依頼側の社内の人が書いている記録の粒度と形式に合わせる。長すぎず、短すぎず |
| チャットの使い方 | 依頼側がチャンネルをどう分けているか、誰に向けて書くか、返信の速さの期待に合わせる。[メールの書き方と運用](/media/fukugyo-mail/) |
| 共有のフォルダの構造 | 依頼側のフォルダの分け方に合わせて置く。自分の分け方で新しいフォルダを作らない |
| 通知と返信の時間 | 依頼側の社内の人が動いている時間と、自分の副業の時間がずれる。返信の時間を最初に伝えておく |
| 面接官や他の部署の人との接点 | 担当者を通すか、直接やり取りしてよいかを決める。ツールで直接連絡できても、運用として通すべき相手がいる |

合わせる要点は、「ツールで直接できることと、運用としてやってよいことは違う」ということです。チャットで面接官に直接メッセージを送れても、依頼側の運用で「面接官への連絡は担当者を通す」と決まっていれば、通します。ツールの機能で判断せず、依頼側の運用で判断します。外部の立場での動き方は[外部の立場だからできること](/media/fukugyo-gaibu-tachiba/)に書いています。

## 自分のツールとの境目

依頼側のツールに合わせても、自分のツールで持つものはあります。境目を決めておきます。

| 自分のツールで持つもの | 依頼側のツールで持つもの |
|---|---|
| 稼働ログ。[稼働ログの付け方](/media/fukugyo-log/) | 候補者の情報と、候補者とのやり取りの記録 |
| 判断のメモ（依頼側の情報を抜いたもの） | 選考の状態と、面接の記録 |
| 自分の側の議事録の控え。[議事録の残し方](/media/fukugyo-gijiroku/) | 依頼側との連絡、社内の人との連絡 |
| 文面の型（依頼側の情報を抜いたもの） | 依頼側向けに調整した文面と、送信の記録 |
| 請求書と入金の記録 | 依頼側が使う稼働の報告の形式（指定があれば） |
| アカウントの一覧。[アカウント管理のしかた](/media/fukugyo-account-kanri/) | 依頼側の共有の資料 |

境目の要点は、「依頼側の情報を含むものは依頼側のツール、自分の記録は自分のツール」です。候補者の情報や依頼側の資料を自分のツールに写さない。逆に、自分の稼働ログや判断のメモを依頼側のツールに置かない。この境目を守ると、案件の終了時に、依頼側のツールはアカウントの停止で終わり、自分のツールには依頼側の情報が残っていない状態になります。自分のツールをどこまで統一するかの考え方は[ツールを統一するか合わせるか](/media/fukugyo-tool-toitsu/)に整理しています。

## 依頼側のツールが使いにくいときの伝え方

依頼側のツールが古い、遅い、使いにくいと感じることはあります。それでも、変えることを求めるのは避けます。

| 状況 | 対応 |
|---|---|
| 操作に時間がかかる | 自分の作業の順番を変える。まとめて入力する時間を決める、入力の型を作る。稼働が増えるなら、報告で伝える |
| 機能が足りない | 「この作業を、このツールの中でどう進めていますか」と依頼側の社内の人のやり方を聞く。社内の人は回避の方法を持っていることが多い |
| 明らかな不具合や設定の問題 | 事実として担当者に伝える。「この操作でこの結果になります」と再現できる形で。直すかどうかは依頼側が決める |
| 別のツールを勧めたくなる | 求められるまで勧めない。外部の担当者がツールの変更を勧めると、依頼側の社内の判断に踏み込むことになる |
| 依頼側から「何か良いツールはないか」と聞かれた | 自分の経験の範囲で、選び方の軸を伝える。特定の製品を勧めるのは、依頼側が比較する段階になってから |
| 使いにくさが稼働に影響している | 稼働の報告に「このツールでの入力に稼働がかかっている」と事実を書き、範囲と稼働の見直しの材料にする。[更新時の条件見直し](/media/fukugyo-keiyaku-koushin-koushou/) |

伝え方の要点は、「変えることを求めず、事実を伝える」ことです。ツールの選定は依頼側の社内の判断で、外部の担当者が「変えたほうがよい」と言うと、その判断に踏み込むことになります。使いにくさが稼働に影響しているなら、それは稼働の事実として報告に書き、範囲と稼働の話として扱います。依頼側の社内の判断に関わる場面は[会社の代表として話す責任](/media/fukugyo-kaisha-daihyou/)にも書いています。

### エラベルの見解

担当する側から見ると、依頼側のツールに合わせられる人は、案件が変わるたびにツールが変わっても、最初の数日で動けています。合わせられない人は、自分のツールに固執して、候補者の情報を自分の側に写し、依頼側の情報管理から指摘を受けるか、依頼側の社内の人と見ているものがずれて、認識の食い違いが起きています。ツールの経験の差ではなく、「依頼側の仕組みの中で動く」という前提の有無の差です。

順番として、案件の最初に、触ってよい範囲を項目の単位で聞き、依頼側の使い方の癖を聞き、自分の範囲の操作だけを覚える。自分の記録は自分のツールに、依頼側の情報は依頼側のツールに、と境目を引く。この順番なら、初めてのツールでも、依頼側の社内の人と同じように動けます。エラベルでは、依頼側が担当者を選ぶとき、ツールの経験より、依頼側の運用に合わせて動けるかを見ている場面が多いです。ツールは変わりますが、合わせ方は変わりません。

## まとめ

- 依頼側のツールに合わせるのが基本。**候補者の情報が依頼側の管理下に留まり・社内の人と同じものを見られ・記録が依頼側に残り・終了時に返すものが少ない**
- 最初に**触ってよい範囲（項目の単位で）・通知の設定・自分の記録の置き場**の三つを決める
- 覚え方は**自分の範囲の操作を書き出し・一度見せてもらい・依頼側の癖を聞き・最初の数件を確認してもらい・手順を一枚にし・分からない操作は触らない**
- **ツールで直接できることと、運用としてやってよいことは違う**。依頼側の運用で判断する
- 境目は**依頼側の情報は依頼側のツール、自分の記録は自分のツール**
- 使いにくくても**変えることを求めず、事実を伝える**。稼働に影響するなら報告に書く

## よくある質問

### 依頼側のATSに、自分の稼働の記録を入れる欄があります。そこに書いてよいですか

依頼側が「そこに書いてほしい」と言うなら、依頼側の求める形で書きます。ただし、自分の稼働ログは自分のツールにも残しておきます。依頼側のツールに書いた記録は、案件の終了時に持ち出せず、請求や更新の根拠として自分の手元に残らないからです。依頼側のツールには依頼側が求める粒度で、自分のツールには自分の管理の粒度で、二か所に持つ形になります。

### 依頼側がチャットを使っておらず、メールと電話だけです

依頼側の運用に合わせます。チャットが無いことを不便に感じても、自分のチャットに招待する形は、依頼側の情報を自分のツールに持ち込むことになるので、依頼側が求めない限りしません。メールでのやり取りの型を整え、返信の時間を伝え、電話が要る場面を決めておけば、チャットが無くても回ります。メールの運用は[メールの書き方と運用](/media/fukugyo-mail/)に整理しています。

### 依頼側から「使いやすいツールを提案してほしい」と頼まれました

頼まれたなら、自分の経験の範囲で、選び方の軸を伝えます。「候補者の状態の管理がしやすいか」「社内の人が使い続けられるか」「既存の媒体と連携できるか」のような軸を示し、依頼側が比較する形にします。特定の製品を一つ勧めると、その製品の不具合や費用の問題が自分の責任に見えることがあるので、複数の候補と軸を示し、選ぶのは依頼側という形にします。提案の仕方は[提案の仕方](/media/fukugyo-teian/)に書いています。
