「採用の状況が一目で分かるダッシュボードを作ってほしい」と頼まれ、グラフを並べた画面を作ると、最初の週は見られ、二週目から誰も開かなくなります。原因は、見た目ではなく、「誰が、いつ、それを見て、何を決めるか」が決まっていないことと、元の記録が更新されずに数字が古くなることです。結論を先に書くと、**採用のダッシュボードは、誰が・いつ・何を見て何を決めるかを先に決め、載せるのはKPI三つ・段階ごとの人数・止まっている候補者の三つだけにし、一覧から最小の関数で出し、グラフより表で、記録の揃いを先に置き、個人情報を載せず、依頼側の人事が自分で直せる形で作ります。**元になる一覧は[スプレッドシートで採用管理を作る](/media/fukugyo-skill-spreadsheet/)に、KPIは[KPIを設計する](/media/fukugyo-skill-kpi/)に、月次の一枚は[レポートを作る](/media/fukugyo-skill-report/)に書いています。ここでは、ダッシュボードの型に絞ります。

## 作られた後に見られなくなる理由

| 状態 | なぜ見られなくなるか |
|---|---|
| グラフが十個並ぶ | どれを見ればよいか分からない |
| 誰が見るかが決まっていない | 全員のためのものは、誰のものでもない |
| いつ見るかが決まっていない | 「随時」は見られない |
| 見て何を決めるかが無い | 見ても行動が変わらない |
| 元の記録が更新されない | 数字が古く、信用されなくなる |
| 作った担当者しか直せない | 壊れたまま放置される |

ダッシュボードは、道具ではなく、「週に一度、決める人が見て、一つ決める」ための場です。場の設計が先で、画面は後です。

## 作る前に決める三つ

| 決めること | 中身 | 例 |
|---|---|---|
| 誰が見るか | 一人か、少人数。決める人と人事の担当 | 採用の責任者と人事の担当の二人 |
| いつ見るか | 曜日と時間。会議の冒頭など、既にある場に置く | 毎週月曜の採用の打ち合わせの最初の五分 |
| 何を見て何を決めるか | 三つの数字を見て、止まっている候補者の次の一歩を決める | KPIの件数を先週と比べ、止まっている候補者の担当に次の一歩を振る |

三つが決まらないうちは、画面を作りません。「見た目を先に作って、使い方は後で」は、見られないダッシュボードになります。

### エラベルの見解

担当する側から見ると、ダッシュボードで最も差がつくのは、「載せるものを三つに絞れるか」です。受ける側は、一覧から出せる数字を全部載せたくなります。経路別、求人別、面接官別、月別の推移。載せるほど、決める人は「で、どこを見ればよいか」となり、開かなくなります。KPIの三つの件数、段階ごとの人数、止まっている候補者。この三つが一画面にあれば、週に一度の五分で足ります。エラベルで担当者を選ぶ企業には、「ダッシュボードを開いて、最初に見る数字は決まっていますか」を、私たちから先に聞いています。受ける側がその場で使える判断としては、載せたい数字が四つ目になったら、「これを見て、何を決めるか」を一行書くこと。書けなければ載せません。書けても、月次のレポートに回します。

## 載せる三つ

| 載せるもの | 中身 | 見て決めること |
|---|---|---|
| KPI三つの件数 | 今週と先週。件数のまま。割合は載せない | 動いているか。動いていなければ手当ての確認 |
| 段階ごとの人数 | 一覧の段階の列を数えたもの。選考中だけ | どの段に人が溜まっているか |
| 止まっている候補者 | 最終更新日が一定の日数を超えた候補者の番号・段階・担当 | 担当に次の一歩を振る |

三つ目が、ダッシュボードの中で最も行動につながります。「止まっている候補者が三人、担当は〇〇」と見えれば、その場で「今日連絡します」となります。週次の確認の型は[ATSの運用ルールを作る](/media/fukugyo-skill-ats-unyou/)に書いています。

## 一覧から最小の仕組みで出す

| 出すもの | 仕組み | 足さないもの |
|---|---|---|
| KPIの件数 | 一覧の該当の列を、期間で数える関数。一つずつ | 割合の計算、推移のグラフ |
| 段階ごとの人数 | 段階の列を数える関数。段階の数だけ | 経路別・求人別の掛け合わせ |
| 止まっている候補者 | 一覧を最終更新日の古い順に並べたフィルタ | 自動の通知、色分けの条件が多いもの |

関数は、依頼側の人事が読んで直せるものだけにします。複雑な集計、外部のツールとの連携、自動の通知は、作った担当者にしか直せなくなり、担当者が替わった瞬間に壊れます。ATSを使っている場合は、ATSの標準の集計の画面で三つが見えるかを先に確かめ、見えるなら別に作りません。

## グラフより表

| グラフ | 表 |
|---|---|
| 推移は見えるが、件数が読めない | 件数がそのまま読める |
| 件数が少ないと、上下が大きく見える | 件数の少なさが分かる |
| 作るのに時間がかかり、直しにくい | 列を足すだけ |
| 見た目で「良い・悪い」の印象が先に来る | 数字を読んでから判断できる |

副業の稼働で扱う件数では、グラフの上下は一件の差で大きく動き、印象を誤らせます。表で件数を並べ、「先週と比べて」を横に置くだけで足ります。どうしてもグラフが要るなら、月次のレポートに一つだけ添えます。

### エラベルの見解

相談で最も多い思い込みは、受ける側の「ダッシュボードができれば、記録が揃う」というものです。実際は逆で、記録が揃っていないダッシュボードは、古い数字と空欄が並び、決める人は一度見て「当てにならない」と閉じます。一度閉じられたダッシュボードは、記録が揃った後も開かれません。順番は、運用ルールで記録を揃える→三か月揃った状態を確かめる→ダッシュボードを作る、です。受ける側がその場で使える判断としては、ダッシュボードの依頼が来たら、まず一覧の「段階」と「最終更新日」の列が直近一か月で埋まっているかを見ること。埋まっていなければ、ダッシュボードの前に運用ルールを提案します。

## 個人情報を載せない

| 載せない | 代わりに |
|---|---|
| 候補者の氏名 | 応募の番号か媒体のID |
| 連絡先、履歴書 | 載せない。一覧の個人情報のシートで |
| 評価の内容 | 載せない。段階と「通す・迷う・通さない」の数だけ |
| 見送り・辞退の理由の自由記述 | 分類の数だけ |

ダッシュボードは、共有の範囲が広がりやすい画面です。決める人と人事の担当だけが見る設定にしても、画面共有や印刷で広がります。個人が特定できる情報を載せない形にしておけば、広がっても問題が小さい。共有の設定は依頼側の管理者が行い、個人情報の扱いに法令が関わる場合は、依頼側の決まりと専門家の確認に従います。個別の判断は専門家にご確認ください。扱いは[個人情報の扱い](/media/fukugyo-kojin-jouhou/)に書いています。

## ダッシュボードとレポートの役割分担

| 役割 | ダッシュボード | レポート |
|---|---|---|
| 頻度 | 週に一度、決める人が自分で見る | 月に一度、担当者が作って渡す |
| 中身 | 三つの数字と止まり。判断は見る人 | 七つの欄。詰まりと判断してほしいことを担当者が書く |
| 形 | 一画面。更新は自動（最小の関数） | 一枚。担当者が読み方を添える |
| 役割 | 「動いているか」「止まっている人は誰か」 | 「どこが詰まりで、何を決めるか」 |

ダッシュボードに「詰まり」や「判断してほしいこと」を書こうとすると、担当者が毎週更新することになり、週次のレポートと同じになります。ダッシュボードは数字だけ、読み方はレポートで、と分けます。レポートの型は[レポートを作る](/media/fukugyo-skill-report/)に書いています。

## よく起きる詰まりと直し方

| 詰まり | 直し方 |
|---|---|
| 依頼側がグラフの多い画面を求める | 三つの表を先に作り、「週に一度の五分で見るもの」と位置づける。グラフは月次のレポートに一つ |
| 誰も開かない | 既にある会議の冒頭に置く。開く時間を決める |
| 数字が古い | 記録の揃いに戻る。運用ルールの週次の確認 |
| 関数が壊れた | 壊れた関数を消し、人事が直せるものだけに戻す |
| 経路別・求人別を載せたい | 月次のレポートの添付に。ダッシュボードには載せない |
| 担当者しか直せない | 関数の一覧と「何を数えているか」の一行を、画面の隅か別シートに残す |

## まとめ

- 見られなくなるのは見た目のせいではなく、**誰が・いつ・何を決めるか**が無いから
- 作る前に**三つを決める**。決まらないうちは画面を作らない
- 載せるのは**KPI三つの件数・段階ごとの人数・止まっている候補者**だけ。四つ目は「何を決めるか」が書けなければ載せない
- 仕組みは**最小の関数**。依頼側の人事が直せるものだけ。ATSの標準の画面で足りるなら作らない
- **グラフより表**。件数のまま、先週と横に
- **記録の揃いが先**。揃っていないダッシュボードは一度見て閉じられる
- **個人情報を載せない**。番号と数だけ。個別の判断は専門家にご確認ください
- ダッシュボードは数字、**読み方と判断はレポート**で

## よくある質問

### 依頼側が有料のBIツールを入れたいと言います

三つの数字を週に一度見るだけなら、一覧の関数で足ります。BIツールは、複数の求人・複数の拠点・複数の年度をまたいで見る段階で効きますが、その段階の前に入れると、設定と保守が担当者に寄り、担当者が替わると止まります。「まず一覧の関数で三か月回し、足りなければツールを検討する」と、順番で提案します。ツールの費用と導入の判断は依頼側です。

### 経営者が「採用の進捗を毎日見たい」と言います

毎日見ても、一日で動く数字は少なく、上下に一喜一憂することになります。「週に一度、月曜に」を提案し、毎日見たいなら「止まっている候補者」の一覧だけを見てもらう形にします。止まっている候補者は毎日変わり、見て行動につながる唯一の項目です。KPIの件数は週で見る、と分けます。

### ダッシュボードの作成は、副業の成果物としてどう扱いますか

三つの表と最小の関数の設計は成果物ですが、画面は依頼側のもので、担当者が持ち出したり他で使い回したりしません。使い回せるのは「三つに絞る型」と「作る前に決める三つ」の考え方だけです。成果物の範囲と、案件の終了後に依頼側が自分で直せる状態にすることを、契約に書きます。範囲の決め方は[業務範囲を書面で固める](/media/fukugyo-scope/)に書いています。
