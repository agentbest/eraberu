本業では、採用の管理は表計算か、担当者の頭の中だった。副業の依頼側は「ATSを使っています」と言う。触ったことがなく、扱えないと案件を受けられないのか、扱えると何が変わるのかが分からない。結論を先に書くと、**ATSを扱えるようになると、「候補者の情報を依頼側の管理下に置いたまま動ける」「自分の記録が依頼側に残る」「工程ごとの数字が取れる」「依頼側の社内の人と同じものを見て話せる」の四つが変わります。**この四つは、副業の担当者が依頼側から信頼される条件（情報の扱い、引き継げる状態、成果の見せ方、社内との協力）に、そのまま重なります。ただし、要るのは特定の製品の操作ではなく、「ATSで採用を回す考え方」で、製品が違っても骨格は同じです。ツールの整理は[よく使うツール](/media/fukugyo-tool-ichiran/)に、依頼側のツールに合わせる進め方は[クライアントのツールに合わせる](/media/fukugyo-kokyaku-tool/)に、記録の残し方は[議事録の残し方](/media/fukugyo-gijiroku/)にまとめています。製品の仕様は、公式の情報で確認してください。

## ATSで扱う情報と役割

ATSが何をする仕組みかを、副業の担当者の視点で整理します。

| ATSが扱うもの | 内容 | 副業の担当者にとっての意味 |
|---|---|---|
| 候補者の情報 | 経歴、連絡先、応募の経路、書類 | 候補者の情報の置き場。ここから出さない |
| 選考の状態 | 応募→書類→面接→内定→承諾の、各候補者の今の工程 | 自分の範囲の工程を進め、状態を更新する場所 |
| 選考の記録 | 面接の評価、連絡の履歴、判断の経緯 | 自分の操作と記録が残る場所。引き継ぎの材料 |
| 社内の連絡 | 面接官への依頼、担当者との共有 | 依頼側の社内の人と、同じ候補者を見て話せる場所 |
| 日程 | 面接の予定、候補者との調整 | 日程調整の記録 |
| 集計 | 工程ごとの人数、通過の割合、期間 | 成果の数字の出どころ。[KPIを設計する](/media/fukugyo-kpi-sekkei-skill/) |

役割の要点は、「ATSは、候補者の情報と選考の記録を、依頼側の管理下に置く仕組み」だということです。副業の担当者が自分の表計算で候補者を管理すると、情報が依頼側の外に出て、記録も依頼側に残りません。ATSの中で動けば、情報は出ず、記録は残り、数字は取れ、社内の人と同じものを見られます。情報の扱いの線は[個人情報の扱い](/media/fukugyo-kojin-jouhou/)に書いています。

## 扱えると変わる四つのこと

ATSを扱えるようになると、副業の担当者の動き方が四つの面で変わります。

| 変わること | ATSを扱えないとき | 扱えるとき |
|---|---|---|
| 一、情報の置き場 | 候補者の情報を自分の表計算や端末で管理し、依頼側の外に出す。終了時に消す作業が要る | 依頼側のATSの中で扱い、自分の側に置かない。終了時はアカウントの停止だけ |
| 二、記録の残り方 | 自分の記録にしか残らず、担当者が状況を聞きに来る。担当者が替わると引き継げない | ATSに残り、担当者はいつでも見られる。担当者が替わっても続く。[いつ辞めても困らない状態を作る](/media/fukugyo-hikitsugi-junbi/) |
| 三、数字の取れ方 | 工程ごとの数字を自分で数える。依頼側の記録と合わない | ATSの集計から取れ、依頼側が確認できる。[数字で語る](/media/fukugyo-suuji/) |
| 四、社内の人との協力 | 面接官や担当者と、別々の情報を見て話す。認識がずれる | 同じ候補者の同じ画面を見て話せる。面接官への依頼もATSの中で |

四つの要点は、「一」の情報の置き場が、他の三つの土台になることです。ATSの中で動くから、記録が残り、数字が取れ、社内の人と同じものを見られます。自分の表計算で動くと、四つとも失われます。ATSを扱えることは、操作の技術ではなく、依頼側の管理下で動くという姿勢の表れです。依頼側の仕組みの中で動く理由は[クライアントのツールに合わせる](/media/fukugyo-kokyaku-tool/)に整理しています。

### エラベルの見解

相談で最も多い思い込みは、「ATSは製品ごとに違うので、特定の製品を覚えないと案件を受けられない」というものです。実際には、ATSの製品は依頼側ごとに違いますが、候補者の状態を工程で進める、記録を残す、連絡を送る、集計を見る、という骨格は共通していて、一つの製品で骨格を覚えれば、次の製品は数日で覚えられます。依頼側の担当者も、外部の担当者が自社のATSを使ったことがあるかは、ほとんど気にしていません。

見ていて差がつくのは、製品の操作を知っているかではなく、「ATSの中で動く」ことを当たり前にしているかです。当たり前にしている人は、初めての製品でも、候補者の情報を自分の側に写さず、記録をATSに残し、担当者が見られる状態を最初から作ります。当たり前にしていない人は、慣れた表計算で管理し、ATSには結果だけを入れ、依頼側から「情報がどこにあるか分からない」と言われています。エラベルでは、担当者が依頼側のATSの中で作業する形を前提にしており、製品の経験は登録の条件にしていません。ATSを扱える、とは、製品を知っていることではなく、依頼側の管理下で動く習慣があることです。

## 製品が違っても共通する骨格

ATSの製品は多くありますが、副業の担当者が使う機能の骨格は共通しています。一つ覚えれば、次に使えます。

| 骨格 | どの製品にもある形 | 自分の範囲で使う場面 |
|---|---|---|
| 候補者の一覧と検索 | 候補者を、状態、職種、応募の経路で絞って見る | 自分の担当の候補者を見つける |
| 候補者の詳細 | 経歴、連絡先、書類、履歴を一画面で見る | 返信の前に経歴を確認する |
| 状態の変更 | 候補者を次の工程に進める、辞退や不合格にする | 自分の範囲の工程で、状態を更新する。触ってよい範囲を最初に確認 |
| 記録の入力 | 連絡の内容、面接の評価、メモを残す | 自分の操作と判断の記録を残す。候補者への連絡の履歴 |
| 連絡の送信 | 候補者へのメールを、ATSから送る。テンプレート | 依頼側の型に沿った連絡。送った記録が残る |
| 面接の設定 | 面接官と候補者の日程を登録し、通知する | 日程調整の記録 |
| 社内への共有 | 面接官に評価を依頼する、担当者にコメントを残す | 担当者を通した社内の人との連携 |
| 集計 | 工程ごとの人数、期間、通過の割合を出す | 稼働報告の数字。[稼働報告のフォーマット](/media/fukugyo-kadou-houkoku/) |

骨格の要点は、「自分の範囲で使うのは、この八つのうち一部」だということです。スカウトの運用と一次対応が範囲なら、候補者の一覧、詳細、状態の変更、記録、連絡の送信を使い、面接の設定と集計は見るだけかもしれません。範囲に応じて使う機能を絞れば、覚える量は少なくて済みます。製品ごとの細かな違いは、依頼側の担当者に聞くか、製品の公式の案内で確認します。

## 依頼側のATSで最初に確認すること

依頼側のATSを使い始める前に、確認することです。確認しないと、依頼側の社内の作業を壊します。

| 確認すること | なぜ | 聞き方 |
|---|---|---|
| 自分専用のアカウントか | 共有だと誰の操作か分からない。[パスワードの受け渡し](/media/fukugyo-password/) | 「私専用のアカウントを発行していただけますか」 |
| 触ってよい範囲 | 状態の変更、評価の入力、削除、連絡の送信のどれを自分がやってよいか | 「候補者の状態を私が進めてよい工程はどこまでですか。評価の欄は面接官の方が書きますか」 |
| 状態の名前の使い方 | 「書類選考中」をどの時点で使うかは、依頼側の運用で決まる | 「状態の名前は、それぞれどの時点で使っていますか」 |
| 記録の書き方 | 社内の人が書いている粒度と形式 | 「記録は、どのくらいの粒度で残していますか。見せていただけますか」 |
| 連絡のテンプレート | 依頼側の型があるか。自分で作ってよいか | 「候補者への連絡の型はありますか。私の範囲の連絡はどの型を使いますか」 |
| 通知の設定 | 本業の時間中に通知が来ない設定にできるか | 「通知は私の側で設定を変えてよいですか」 |
| 見えるが触らない範囲 | 権限で見えても、自分の範囲外の情報（他の職種、給与）は見ない | 「見えるが私の範囲外の情報があれば教えてください。触りません」 |
| 集計の取り方 | 稼働報告に使う数字を、どの画面から取るか | 「工程ごとの人数は、どの画面で見られますか」 |

確認の要点は、「触ってよい範囲を、工程と項目の単位で聞く」ことです。「ATSを使ってください」だけでは、候補者を次の工程に進めるのが自分か担当者か、評価を書くのが誰かが分かりません。工程と項目で聞いておけば、社内の人の作業と重なりません。確認の全体は[初回打ち合わせの進め方](/media/fukugyo-shodan/)に、依頼側の運用に合わせる線は[クライアントのツールに合わせる](/media/fukugyo-kokyaku-tool/)に書いています。

## ATSが無い依頼側でどうするか

依頼側にATSが無い（表計算か、担当者の頭の中で管理している）場合、ATSを扱える力は、別の形で活きます。

| 状況 | どうするか |
|---|---|
| 依頼側に候補者の管理の仕組みが無い | 依頼側の共有の中に、候補者の一覧の表を作ることを提案する。列は、ATSの骨格（状態、工程の日付、記録、連絡の履歴）に合わせる。自分の側には置かない |
| 表はあるが、状態の管理が無い | 状態の列を足し、工程で管理する形を提案する |
| 記録が残っていない | 記録の列を足し、自分の範囲の記録を残す。社内の人にも同じ形を勧める |
| 集計が無い | 表から工程ごとの人数を出す形を作る。稼働報告の数字にする |
| 依頼側がATSの導入を検討している | 自分の経験の範囲で、選び方の軸（工程の管理、記録、集計、社内の共有）を伝える。特定の製品は勧めない。[他社事例をどう扱うか](/media/fukugyo-benchmark/) |

無い場合の要点は、「ATSの骨格を、依頼側の共有の中に表で作る」ことです。ATSを扱える人は、ATSの骨格（状態、記録、連絡、集計）を知っているので、ATSが無くても、その骨格で表を作れます。表は依頼側の共有の中に作り、依頼側の資産として残します。自分の表計算に作ると、情報が依頼側の外に出ます。依頼側に型が無い場合の進め方は[どんな会社から依頼が来るのか](/media/fukugyo-qa-11/)に整理しています。

## ATSを使う上での失敗

ATSを使う中で、副業の担当者が起こしやすい失敗です。

| 失敗 | 何が起きるか | 防ぎ方 |
|---|---|---|
| 候補者の情報をATSから自分の端末に落とす | 情報が依頼側の外に出る。終了時に消し忘れる | ATSの中で見る。落とさない。[私物端末で作業してよいか](/media/fukugyo-tanmatsu/) |
| 範囲外の状態を変える | 面接の評価や合否を、自分が進める | 触ってよい範囲を最初に確認し、範囲外は担当者に |
| 記録を残さない | 自分の操作がATSに残らず、担当者が状況を聞きに来る | 動いたら一行、ATSに残す |
| 依頼側の運用と違う状態の使い方をする | 社内の人が状況を誤解する | 状態の名前の使い方を最初に聞く |
| 共有のアカウントで操作する | 誰の操作か分からない。規約に触れる | 専用の発行を頼む |
| 見える範囲外の情報を見る | 権限の範囲を超えた閲覧。信頼の問題 | 見えても触らない。権限を絞ってもらう |
| ATSの集計を見ずに、感覚で報告する | 数字が依頼側の記録と合わない | 稼働報告の数字はATSの集計から。[数字で語る](/media/fukugyo-suuji/) |
| 契約が終わってもログインする | 停止されていなくても、契約後に入れば無断で情報に触れたことになる | 停止を依頼し、入らない。[アカウント管理のしかた](/media/fukugyo-account-kanri/) |

失敗の要点は、「情報を落とさない」と「範囲外を触らない」の二つに集約されます。この二つは、ATSの操作の問題ではなく、情報の扱いと範囲の問題で、ATSに限らず副業の全体に通じる線です。

## 経験が無い人の覚え方

ATSを使ったことが無い人が、最初の案件で覚える手順です。全部を覚える必要はありません。

| 手順 | 内容 |
|---|---|
| 一、自分の範囲で使う機能を書き出す | 骨格の八つのうち、自分の範囲で使うものだけ。スカウトと一次対応なら、一覧、詳細、状態の変更、記録、連絡の送信 |
| 二、担当者に一度、画面を見せてもらう | 自分の範囲の操作を一通り。全機能の説明は要らない |
| 三、依頼側の運用の癖を聞く | 状態の名前の使い方、記録の粒度、誰がどの欄を書くか |
| 四、最初の数件を担当者に確認してもらう | 自分が入力した状態と記録が、依頼側の運用と合っているか |
| 五、自分用の手順を一枚にする | 自分の範囲の操作と、依頼側の癖を、依頼側の情報を含まない形で一枚に |
| 六、分からない操作は触らない | 影響が分からない操作は、担当者に聞くまで触らない |
| 七、次の案件で別の製品に会ったら、骨格で対応する | 一覧、詳細、状態、記録、連絡、面接、共有、集計の八つを探せば、どの製品でも動ける |

覚え方の要点は、「三」の依頼側の運用の癖を聞くことです。同じ製品でも、会社によって状態の名前の使い方や、誰がどの欄を書くかが違います。製品の説明書には無い、その会社の運用を聞いておけば、製品に慣れていなくても、社内の人と同じ使い方ができます。初めてのツールの覚え方は[クライアントのツールに合わせる](/media/fukugyo-kokyaku-tool/)に整理しています。

### エラベルの見解

担当する側から見ると、依頼側から「ATSの扱いが上手い」と言われている人は、製品に詳しい人ではなく、ATSの中で動くことを徹底している人です。候補者の情報をATSから出さず、自分の操作と記録をATSに残し、稼働報告の数字をATSの集計から取り、社内の人と同じ画面を見て話す。製品が変わっても、この動き方は変わりません。製品に詳しくても、自分の表計算で管理し、ATSには結果だけを入れている人は、依頼側から「情報がどこにあるか分からない」と言われています。

順番として、案件の最初に専用のアカウントと触ってよい範囲と運用の癖を確認し、自分の範囲で使う機能だけを覚え、候補者の情報をATSから出さず、動いたら記録を残し、数字はATSの集計から取り、契約が終わったら停止を依頼して入らない。この順番で、ATSを扱えることは、製品の知識ではなく、依頼側の管理下で動く習慣になります。エラベルでは、担当者が依頼側のATSの中で作業する形を前提にしており、製品の経験は登録の条件にしていません。ATSを扱える、とは、依頼側が「情報がどこにあるか分かる」状態を作れることです。

## まとめ

- ATSを扱えると**情報の置き場・記録の残り方・数字の取れ方・社内の人との協力**の四つが変わる。情報の置き場が土台
- 要るのは**製品の操作ではなく、ATSで採用を回す考え方**。骨格（一覧・詳細・状態・記録・連絡・面接・共有・集計）は製品が違っても共通
- 最初に**専用のアカウント・触ってよい範囲（工程と項目で）・状態の名前・記録の書き方・テンプレート・通知・見えるが触らない範囲・集計の取り方**を確認
- ATSが無い依頼側では**骨格を依頼側の共有の中に表で作る**。自分の側には置かない
- 失敗は**情報を落とす・範囲外を触る・記録を残さない・運用と違う使い方・共有アカウント・範囲外を見る・感覚で報告・終了後にログイン**
- 覚え方は**自分の範囲の機能だけ・一度見せてもらう・運用の癖を聞く・最初の数件を確認してもらう・手順を一枚に・分からない操作は触らない・次は骨格で対応**

## よくある質問

### 依頼側のATSが使いにくく、自分の表計算で管理したほうが速いです

速く見えても、候補者の情報が依頼側の外に出て、記録が依頼側に残らず、担当者が状況を見られなくなります。依頼側から見れば、速さより「情報がどこにあるか分からない」ほうが問題です。使いにくさは、自分の範囲の操作を手順の一枚にし、まとめて入力する時間を決めることで減らします。それでも稼働に影響するなら、稼働報告に「入力に稼働がかかっている」と事実を書き、範囲と稼働の見直しの材料にします。ツールの変更を依頼側に求めることは、依頼側の判断に踏み込むので避けます。使いにくいときの扱いは[クライアントのツールに合わせる](/media/fukugyo-kokyaku-tool/)に書いています。

### ATSに自分の稼働の記録も入れるよう言われました

依頼側が求めるなら、依頼側の形式でATSに入れますが、自分の稼働ログは自分のツールにも残します。ATSに入れた記録は、契約の終了後に持ち出せず、請求や更新の根拠として自分の手元に残らないからです。ATSには依頼側が求める粒度で、自分のログには自分の管理の粒度で、二か所に持ちます。自分のログを先に付け、ATSに写す流れにすれば、負担は大きくなりません。ログの付け方は[稼働ログの付け方](/media/fukugyo-log/)に整理しています。

### 本業でATSを使っていますが、その経験を副業の経歴に書いてよいですか

「ATSを使った採用管理の経験」として、製品の種類と、使った機能の骨格（状態の管理、記録、集計）を書くことはできます。本業の会社名や、本業の採用の内情（候補者の数、社内の運用の詳細）は、本業の情報なので書きません。「ATSで候補者の状態の管理と記録を担当した経験が〇年」のように、骨格と年数で書けば、依頼側は「ATSの中で動ける人」と判断できます。本業の情報の線は[本業と利益相反になる案件](/media/fukugyo-riekisouhan/)に、経歴の書き方は[プロフィールの書き方](/media/fukugyo-profile/)に書いています。
