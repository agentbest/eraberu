「ATSを入れたい。どれがよいか選んでほしい」という依頼で、機能の比較表を作って渡すと、依頼側は一番機能が多いものを選び、半年後に「使いこなせていない」となります。ATSは、機能の多さで選ぶものではなく、「依頼側の選考の段階と、毎日使う画面と、誰が更新するか」に合うかで選ぶものです。結論を先に書くと、**ATSの選定は、依頼側の選考の段階と一致するか・毎日使う三つの画面が使いやすいか・誰が更新するかに合うかの三つの軸で行い、料金や機能は確認してから比べ、初期設定では選考の段階・項目・権限・通知・テンプレートを決め、既存の記録から順に移し、個人情報の権限を先に設計し、導入の判断は依頼側に残します。**会社側から見た選び方は[ATSの選び方](/media/rpo-ats-erabikata/)に、使いこなせない構造は[ATSを入れたが使いこなせていない](/media/rpo-ats-tsukaikonasenai/)に、案件として受ける形は[ATS導入の支援の副業の実務](/media/fukugyo-ats-dounyu-shigoto/)に書いています。ここでは、選定と初期設定の型に絞ります。

## 機能の一覧で選ぶと使われなくなる

| 選び方 | 何が起きるか |
|---|---|
| 機能の数が多いもの | 使う画面が多すぎて、誰も全部を覚えない。更新が止まる |
| 有名なもの | 依頼側の選考の段階と合わず、段階を無理に合わせることになる |
| 安いもの | 必要な項目や権限が無く、結局スプレッドシートに戻る |
| 媒体の営業が勧めたもの | 媒体との連携は良いが、他の経路（紹介、リファラル）が入らない |
| 担当者が前職で使っていたもの | 依頼側の規模と体制が違う |

ATSが使われるかどうかは、「毎日使う三つの画面（候補者の一覧、一人の詳細、次にやること）」が、更新する人にとって楽かどうかで決まります。

## 選定の三つの軸

| 軸 | 確かめること | 確かめ方 |
|---|---|---|
| 選考の段階と一致するか | 依頼側の段階（応募→書類→一次→二次→最終→内定→入社）を、そのまま設定できるか。段階の名前を変えられるか | 依頼側の段階を先に一枚にしてから、各ATSで再現できるかを見る |
| 毎日使う三つの画面 | 一覧で「いま誰がどの段階か」が一目で分かるか。一人の詳細で記録が書けるか。「次にやること」が出るか | 無料の試用があれば、依頼側の更新する人に触ってもらう |
| 誰が更新するかに合うか | 更新する人（人事、現場の面接官、副業の担当者）が、それぞれ自分の画面だけで済むか。権限を分けられるか | 更新する人の一覧と、各人が触る画面を先に決める |

三つの軸を、依頼側の状況で先に埋めてから、候補を見ます。候補から先に見ると、機能に引っ張られます。媒体の選定の根拠の作り方と同じ考え方で、[媒体を提案する根拠の作り方](/media/fukugyo-skill-baitai-sentei/)に書いています。

### エラベルの見解

担当する側から見ると、ATSの選定で最も差がつくのは、「依頼側の選考の段階を先に一枚にしているか」です。受ける側は、ATSの候補を先に並べ、それぞれの機能を比べます。ただ、依頼側の選考が「一次は現場、二次は人事と現場、最終は経営者」で、段階ごとに記録の形が違うなら、その形をそのまま設定できないATSは、どれだけ機能が多くても合いません。段階と記録の形を一枚にしてから候補を見ると、候補は二つか三つに絞られます。エラベルで担当者を選ぶ企業には、「ATSを選ぶ前に、御社の選考の段階と記録の形を一枚にしていますか」を、私たちから先に聞いています。受ける側がその場で使える判断としては、[面接の設計](/media/fukugyo-skill-mensetsu-sekkei/)の五つ（段階・面接官・項目・記録・決める人）を、そのままATSの要件の一枚にすること。設計が無い依頼側では、ATSの選定より先に設計をします。

## 料金や機能を断定しない

ATSの料金、プランの内容、機能の有無、連携できる媒体は変わります。「〇〇は月〇〇円で〇〇ができます」と提案に書いて、契約の段階で違っていると、担当者の信頼が落ちます。

| 断定する書き方 | 置き換え |
|---|---|
| 「月額〇〇円」 | 「料金はアカウント数と期間で変わるため、見積もりを取ってから比べる」 |
| 「〇〇の機能がある」 | 「〇〇の機能の有無と制約は、試用か担当者への確認で確かめる」 |
| 「〇〇媒体と連携できる」 | 「連携の可否と条件は、契約前に確認する」 |

比べるときは、「同じ段階を再現できるか」「同じ人が同じ画面で更新できるか」で軸をそろえます。費用の判断は依頼側です。担当者は軸をそろえ、候補を二つか三つに絞り、確認する項目を並べるまでです。

## 初期設定で決めること

| 決めること | 中身 | 決める人 |
|---|---|---|
| 選考の段階 | 依頼側の段階をそのまま。名前も依頼側の呼び方に | 依頼側（担当者が一枚を作る） |
| 項目 | 候補者の一覧に出す項目（段階、担当、次の日程、経路）。詳細に書く項目（評価シートの観点） | 担当者が案、依頼側が決定 |
| 権限 | 誰が何を見られるか、書けるか。面接官は自分の段の記録だけ。個人情報の閲覧は最小に | 依頼側の決まりに従う |
| 通知 | 誰に何を知らせるか。日程が決まったら面接官に、記録が書かれたら決める人に。多すぎると無視される | 担当者が案 |
| テンプレート | 候補者への連絡の文面（日程の提示、確定、結果）。[返信対応のテンプレート](/media/fukugyo-skill-henshin-taiou/)の型 | 担当者が案、依頼側が確認 |

初期設定は、「最初から全部」ではなく、「毎日使う三つの画面が動く最小」で始めます。段階と項目と権限が決まれば動きます。通知とテンプレートは、動き始めてから足します。

## 既存の記録からの移行

| 順 | 移すもの | 注意 |
|---|---|---|
| 一 | 選考中の候補者（いま動いている人） | 段階と次の日程を正確に。ここが間違うと候補者に迷惑がかかる |
| 二 | 直近の応募者（結果が出た人） | 依頼側の決まりで保管の対象になっている範囲だけ |
| 三 | 過去の応募者 | 移すかどうかは依頼側の決まり。保管の期限が過ぎたものは移さない |
| 四 | 媒体との連携 | 連携の設定は、一〜三が終わってから。連携で重複が入らないように |

移行は、個人情報を扱う作業です。移す範囲、移した後の元のデータの扱い（消すか残すか）、移す作業を誰が行うかは、依頼側の決まりに従います。担当者の端末に候補者の情報をダウンロードして作業することは避け、依頼側の環境で行います。情報の扱いは[情報の取り扱いと端末の分離](/media/fukugyo-security/)に書いています。

### エラベルの見解

相談で最も多い思い込みは、受ける側の「ATSを入れれば、採用の管理が整う」というものです。実際には、ATSは記録の置き場所で、記録の形（段階・観点・事実と判断）が決まっていなければ、置き場所が変わるだけで管理は整いません。スプレッドシートで回らなかった理由が「記録の形が無い」ことなら、ATSに移しても同じです。ATSの選定の前に、記録の形を決める。それができていれば、スプレッドシートでも回ることがあります。受ける側がその場で使える判断としては、依頼側が「ATSを入れたい」と言ったとき、まず「いまの記録の形」を見せてもらうこと。形が無ければ、選定の前に形を作る提案をします。形があれば、その形を再現できるATSを選びます。

## 個人情報と権限の設計

| 決めること | 考え方 |
|---|---|
| 誰が候補者の詳細を見られるか | 最小に。面接官は自分の段の候補者だけ。経営者は最終の候補者だけ |
| 誰が個人情報（連絡先、履歴書）を見られるか | 人事と、日程調整を担う人だけ。面接官には評価シートの観点だけ見せられる形が望ましい |
| 副業の担当者のアカウント | 依頼側が発行し、依頼側が管理。権限は担当者の業務に要る範囲だけ。案件の終了時に依頼側が停止 |
| 保管の期限 | 依頼側の決まりに従う。ATSの設定で自動で消える形があれば、依頼側の決まりに合わせて設定 |
| 外部への共有 | ATSの外に候補者の情報を出す（ダウンロード、メールで送る）ことの可否と範囲 |

権限の設計は、個人情報の扱いに関わり、法令上の整理があります。依頼側の決まりと専門家の確認に従い、担当者が「これで十分」と判断しません。個別の判断は専門家にご確認ください。担当者自身のアカウントの扱いは[アカウント管理のしかた](/media/fukugyo-account-kanri/)に書いています。

## 導入の判断は依頼側

| 担当者がやること | 依頼側が決めること |
|---|---|
| 選考の段階と記録の形を一枚にする | どのATSと契約するか |
| 三つの軸で候補を二つか三つに絞る | 費用の判断 |
| 確認する項目（料金・機能・連携・権限）を並べる | 権限と保管の決まり |
| 初期設定の案と移行の順番を作る | 移行の範囲と作業の担当 |
| 試用の結果（更新する人が触った感想）を整理する | 導入の可否 |

契約や費用の判断に担当者が踏み込むと、後で「担当者が勧めたから」となります。担当者は材料を整えるまでです。

## よく起きる詰まりと直し方

| 詰まり | 直し方 |
|---|---|
| 依頼側が機能の多さで選びたがる | 「毎日使う三つの画面」を更新する人に触ってもらい、感想で比べる |
| 選考の段階が決まっていない | ATSの前に[面接の設計](/media/fukugyo-skill-mensetsu-sekkei/)の五つを一枚に |
| 料金をすぐ知りたがる | 「見積もりを取ってから比べる」を提案に入れる。担当者は数字を言わない |
| 全機能を最初から設定しようとする | 段階・項目・権限の最小で動かし、通知とテンプレートは後から |
| 移行で候補者の情報が担当者の端末に | 依頼側の環境で作業する形に戻す。ダウンロードしない |
| 面接官が使わない | 面接官の画面を「自分の段の候補者と評価シートだけ」に絞る。権限で見えるものを減らす |

## まとめ

- 機能の多さで選ぶと使われなくなる。**毎日使う三つの画面**が更新する人にとって楽かで決まる
- 選定の軸は**選考の段階と一致するか・三つの画面・誰が更新するか**。依頼側の状況を先に一枚にしてから候補を見る
- **料金・機能・連携は断定しない**。確認してから比べる
- 初期設定は**段階・項目・権限**の最小で動かし、**通知・テンプレート**は後から
- 移行は**選考中の候補者から**。担当者の端末に落とさず、依頼側の環境で
- **個人情報の権限は最小に**。担当者のアカウントは依頼側が発行・管理・停止。個別の判断は専門家にご確認ください
- **導入の判断は依頼側**。担当者は材料を整えるまで

## よくある質問

### 依頼側の規模が小さく、ATSは要らないのではないかと思います

その判断も材料として伝えます。「選考の段階と記録の形が決まっていれば、スプレッドシートで回ることがあります」と、ATSを入れない案を並べます。ATSが要るかどうかは、候補者の数と更新する人の数と、媒体との連携の必要で決まり、規模だけでは決まりません。入れない案を含めて依頼側が判断できる形にします。

### 副業の担当者が、ATSの管理者権限を持ってもよいですか

依頼側の決まりに従います。管理者権限は、権限の設定と個人情報の一括の操作ができるので、担当者が持つと、依頼側の管理の外に出ます。初期設定の期間だけ依頼側の管理者と一緒に設定し、設定が終わったら担当者の権限を業務に要る範囲に下げる形を提案します。案件の終了時には、依頼側がアカウントを停止します。

### 既存のATSから別のATSに乗り換えたいと言われました

乗り換えは、移行の負担と、既存の記録の扱いが大きい。「使いこなせていない」が理由なら、乗り換えではなく、[ATSを入れたが使いこなせていない](/media/rpo-ats-tsukaikonasenai/)の型（三つの画面と更新の担当に絞る）で直るかを先に見ます。段階が再現できない、権限が分けられない、など既存のATSの構造の問題なら乗り換えの候補を絞ります。乗り換えの判断は依頼側で、担当者は「直る問題か、構造の問題か」を分けて渡します。
