プロダクトマネージャーの採用を代行に出すとき、他の職種と同じように「探して連れてきてほしい」と頼むと、代行は「プロダクトマネージャー」の肩書で探し、来る人は会社の想定とずれます。この職種は、会社によって担う範囲がまったく違い、何を作るかを決める人もいれば、決まったものを進める人もいて、数字の責任を持つ人もいれば持たない人もいます。結論を先に書くと、**プロダクトマネージャー採用で代行に出せるのは「探す・届ける・一次対応する・進捗を回す」で、「自社のプロダクトマネージャーが何を決める役割かの定義・判断の質の評価・経営やエンジニアとの関係の設計」は社内に残す**のが線です。役割の定義が無い募集は、代行に出しても社内で回しても、面談で噛み合いません。母集団形成の順番は[プロダクトマネージャーの母集団形成](/media/rpo-pdm-boshuudan/)に、要件の作り方は[プロダクトマネージャーの採用要件の作り方](/media/rpo-pdm-youken/)にまとめています。

## プロダクトマネージャー採用が他の職種と違う点

一つ目は、役割の定義が会社ごとに違うことです。「何を決めるか」（作るものを決めるのか、優先順位を決めるのか）、「誰と決めるか」（経営と直接か、開発側の責任者とか、事業側とか）、「どこまで担うか」（決めるところまでか、進める実務も持つか）、「数字を持つか」（売上や利用数の指標に責任を持つか）。この四つの組み合わせで、同じ肩書でも別の仕事になります。候補者は自分の経験に近い姿を想定して応募するので、四つが求人票に無いと、面談でずれます。

二つ目は、「決める役割」を外部が評価しにくいことです。プロダクトマネージャーの力量は、判断の質（何を作らないと決めたか、優先順位をどう付けたか、その根拠）に表れますが、経歴には「〇〇のプロダクトを担当」としか書かれません。判断の質を見るには、自社のプロダクトを分かっている人が面接で聞く必要があります。

三つ目は、経営との距離が採用を左右することです。プロダクトマネージャーは、経営の方針とプロダクトの判断をつなぐ役割で、経営が「決めたことを実行してほしい」のか「決めてほしい」のかで、求める人が変わります。経営がどちらを求めているかが曖昧だと、入社後に「決めさせてもらえない」「決めてくれない」のどちらかになります。

四つ目は、市場の中で、経験の幅が広いことです。事業会社で数字の責任を持ってきた人、開発側から企画に移った人、コンサルティング会社から転向した人、営業から転向した人。同じ肩書で、来た道が全く違い、自社の役割に合うかは肩書では分かりません。

この四つから、代行に出せる工程が決まります。

## 工程ごとの「任せられる・残す」

| 工程 | 任せられるか | 理由 |
|---|---|---|
| 役割の定義（何を・誰と・どこまで・数字） | 残す | 経営とプロダクトの責任者でしか決められない |
| 経営やエンジニアとの関係の設計 | 残す | 誰が最終的に決めるか。プロダクトマネージャーに何を委ねるか |
| 要件の決定 | 残す | 役割の定義から。外部は整理を手伝える |
| 求人票の作成 | 任せられる（四つが決まっていれば） | 決まったものを候補者に伝わる言葉にする |
| 媒体の選定と運用 | 任せられる | プロダクト職に届く媒体と経路の経験があれば |
| スカウトの検索と送信 | 任せられる | 役割に合わせた検索と、文面の個別化 |
| 応募者への一次対応 | 任せられる | 連絡、日程、流れの案内 |
| 書類の一次絞り | 条件付き | 経歴の分類（決める役割か進める役割か、数字を持ったか）は任せられる。判断の質は残す |
| 判断の質の評価 | 残す | 自社のプロダクトを分かる人が面接で聞く。外部は評価の型作りと記録 |
| 合否の判断 | 残す | 会社の判断 |
| 条件の決定と提示 | 残す | 会社の判断 |
| 内定後の対応 | 任せられる | 辞退を防ぐ連絡 |

線の要点は、「役割の定義の四つが、募集の前に社内で決まっているか」です。この四つが求人票とスカウトの中身になり、候補者が「自分の経験に合うか」を判断する材料になります。

### エラベルの見解

相談で多いのは、「プロダクトマネージャーを募集しているが、面談で話が噛み合わない」というご相談です。求人票を見ると、「プロダクトマネージャー募集。プロダクトの企画・推進」と書かれていて、何を決めるのか、誰と決めるのか、数字を持つのかが無い。応募者は、自分の前職の姿（数字を持って決めていた、または決まったものを進めていた）を想定して来て、面談で「うちはそうではない」となります。求人票が役割を決めていません。

見ていて差がつくのは、「経営者が『プロダクトマネージャーに何を決めてほしいか』を一文で言えるか」です。「作るものと優先順位を、経営と相談しながら決めてほしい。数字の責任は事業側が持つ」と言えるなら、募集が書けます。「良い人が来たら任せたい」なら、役割が決まっていません。エラベルでは、プロダクトマネージャーの案件をお受けする前に、依頼側の経営者に四つを伺い、一文にしていただいています。一文ができない会社は、採用の前に、経営者がプロダクトの判断をどこまで委ねるかを決める必要があります。

## 代行に出す前に社内で確認すること

代行に出す前に、社内で揃えておくことを六つ挙げます。

- **四つの役割の定義が一文で言えるか。** 何を決めるか、誰と決めるか、どこまで担うか、数字を持つか
- **経営が、プロダクトの判断をどこまで委ねるか決めているか。** 「決めてほしい」のか「決めたことを実行してほしい」のか。曖昧なら入社後にずれる
- **エンジニアの責任者が、プロダクトマネージャーとの関係を理解しているか。** 誰が何を決めるか。エンジニアが「指示されるだけ」と感じる関係だと、入社後に対立する
- **自社のプロダクトの現状と課題を、候補者に伝えられる形にしているか。** 何を作っていて、何が課題で、次に何を決める必要があるか。求人票とスカウトの中身になる
- **判断の質を評価する人がいるか。** 自社のプロダクトを分かっていて、候補者の判断の根拠を聞ける人。経営者本人か、プロダクトの責任者
- **面接に経営者とエンジニアの責任者が出られるか。** プロダクトマネージャーは両方と働く。両方が面接に出ないと、候補者は関係を確かめられない

六つのうち、一つ目と二つ目が最も重要です。役割の定義と、経営がどこまで委ねるかが決まれば、他は整理できます。

## プロダクトの責任者がいない会社の組み方

一人目のプロダクトマネージャーを採る会社、または経営者がプロダクトを見ていて責任者がいない会社は多い。組み方を三つ示します。

一つ目は、経営者が「どこまで委ねるか」を先に決め、求人票に書くことです。「作るものの決定は経営者が持ち、優先順位と仕様の決定を任せる」「作るものから任せるが、経営会議で承認を取る」。委ねる範囲を正直に書けば、その範囲に合う人が応募します。「全部任せる」と書いて実際は経営者が決める、という形が最も離職を生みます。

二つ目は、エンジニアの責任者を、要件と面接に巻き込むことです。プロダクトマネージャーはエンジニアと一緒にプロダクトを作る役割で、エンジニアの責任者が「どういうプロダクトマネージャーなら一緒にやれるか」を言えないと、要件が定まりません。

三つ目は、外部のプロダクトの経験者を、要件の整理と面接だけに入れることです。顧問、業務委託、知人。「自社の状態で、プロダクトマネージャーに何を委ねるのが現実的か」を整理してもらい、面接で判断の質を聞いてもらう。代行とは別の役割です。

どの組み方でも、「役割の定義を代行に任せない」ことは同じです。

## 代行を選ぶときの確認項目

| 確認項目 | 聞き方 | 見るポイント |
|---|---|---|
| プロダクトマネージャー採用の経験 | 「プロダクトマネージャーの採用で、役割の定義の整理から関わった経験はありますか」 | 肩書で探すだけでないか |
| 役割の理解 | 「当社のプロダクトマネージャーの役割を、候補者向けの言葉にするとどうなりますか」 | 四つ（何を・誰と・どこまで・数字）を言えるか |
| 経歴の読み方 | 「『プロダクトマネージャーとして〇〇を担当』という経歴を、どう読みますか」 | 決める役割だったか、数字を持ったかを確かめる姿勢があるか |
| 媒体と経路 | 「プロダクト職に届く経路は何ですか」 | 転向層（開発、事業、コンサル）を知っているか |
| 評価の扱い | 「判断の質の評価はどう進めますか」 | 「御社で」と答えるか |
| 担当者 | 「担当する方の経歴を教えてください」 | プロダクト職か近い職種の採用経験があるか。[担当者の経歴を確認する](/media/rpo-tantousha-keireki/) |

確認の要点は、「経歴の読み方」の答え方です。「プロダクトマネージャーの肩書があれば経験者」と読む代行は、進める役割だった人を決める役割の候補として紹介します。

## 代行に出したあとに起きること

| 起きること | 戻し方 |
|---|---|
| 合わない応募が増える | 求人票に四つを書く。[プロダクトマネージャーの母集団形成](/media/rpo-pdm-boshuudan/) |
| 面談で「決めさせてもらえるのか」と聞かれ、答えられない | 経営が委ねる範囲を決め、求人票とスカウトに書く |
| エンジニアの責任者が面接に出ず、入社後に対立する | エンジニアの責任者の面接の枠を先に固定する |
| 代行が判断の質を評価し始める | 「評価は社内で」と戻す。代行は経歴の分類まで |
| 入社後、経営者が結局全部決めて、本人が離れる | 採用の工程の外だが、委ねる範囲を経営者が守る。守れないなら、募集の段階で「実行が中心」と書く |

戻し方の要点は、「経営が委ねる範囲を、求人票の段階で正直に書く」ことです。「全部任せる」と書いて実際は違う、が最も離職を生みます。

### エラベルの見解

担当する側から見ると、プロダクトマネージャーの採用で最も難しいのは、依頼側の経営者が「どこまで委ねるか」を決めることです。経営者は「良い人が来たら任せたい」と言いますが、実際にプロダクトの判断を手放せるかは、決めてみないと分かりません。ここが曖昧なまま募集すると、決める役割を期待した候補者が来て、入社後に「決めさせてもらえない」となります。

エラベルでは、プロダクトマネージャーの案件をお受けするとき、依頼側の経営者に「作るものの決定を手放せるか」を直接伺っています。手放せるなら「決める役割」の募集、手放せないなら「優先順位と仕様を決め、実行を担う役割」の募集として、正直に整理します。後者でも、合う人はいます。前者と書いて後者だった、が最も不幸です。

## まとめ

- プロダクトマネージャー採用で代行に出せるのは**探す・届ける・一次対応する・進捗を回す**。**役割の定義・判断の質の評価・経営やエンジニアとの関係の設計**は社内に残す
- 他の職種と違うのは**役割の定義が会社ごとに違う（何を・誰と・どこまで・数字）・決める役割は外部が評価しにくい・経営との距離が採用を左右する・経験の幅が広い**
- 代行に出す前に**四つの一文・経営が委ねる範囲・エンジニアの責任者の理解・プロダクトの現状と課題の言語化・判断の質を評価する人・経営者とエンジニアの責任者の面接の枠**を確認
- 責任者がいなければ**経営者が委ねる範囲を先に決めて正直に書く・エンジニアの責任者を要件と面接に巻き込む・外部のプロダクトの経験者を整理と面接だけに**
- 代行を選ぶときは**経歴の読み方**の答え方を見る
- **経営が委ねる範囲を求人票の段階で正直に書く**。「全部任せる」と書いて違う、が最も離職を生む

## よくある質問

### 経営者がプロダクトの判断を手放せるか、自分でも分かりません

手放せるかどうかを、採用の前に試す方法があります。いま社内で、プロダクトの判断（次に作る機能、優先順位）を、経営者以外の誰か（開発の責任者、事業の責任者）に一度委ねてみて、その判断に経営者が口を出さずにいられるか。口を出してしまうなら、手放せない状態で、募集は「優先順位と仕様を決め、実行を担う役割」として正直に書きます。口を出さずにいられるなら、「決める役割」として書けます。試さずに「任せたい」と書くと、入社後に試すことになり、本人が離れます。

### プロダクトマネージャーの経験者が少なく、母集団が作れません

経験者だけを待つと作れません。開発側から企画に関心のある人、事業側で数字を持って企画をしてきた人、コンサルティング会社で事業の企画に関わった人は、プロダクトマネージャーの肩書は無くても、役割の一部を経験しています。役割の定義に合わせて、どの転向元が合うかを決め（数字を持つ役割なら事業側、開発と近い役割なら開発側）、要件を肩書ではなく経験の中身で書けば、母集団に入ります。[プロダクトマネージャーの採用要件の作り方](/media/rpo-pdm-youken/)を参照してください。

### エンジニアの責任者が「プロダクトマネージャーは要らない。自分たちで決められる」と言っています

その状態でプロダクトマネージャーを採ると、入社後にエンジニアと対立します。採用の前に、経営者とエンジニアの責任者で「なぜプロダクトマネージャーが要るのか」「エンジニアが決めることと、プロダクトマネージャーが決めることをどう分けるか」を話し、エンジニアの責任者が納得する形を作ります。納得しないなら、プロダクトマネージャーの採用より、エンジニアの責任者にプロダクトの判断を委ねる形のほうが合うこともあります。エンジニアの責任者を面接に出すのは、この関係を候補者に確かめてもらうためでもあります。
