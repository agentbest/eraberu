IT・Web業界の会社が採用代行を検討するとき、「エンジニアが採れないから、採用のプロに任せたい」という動機が多い。ただ、IT・Web業界の採用は、他の業界と比べて「職種が細かく分かれている」「候補者が複数の会社を同時に見ている」「技術の見極めを社外に出しにくい」という三つの難しさがあり、全部を任せる形は最も失敗しやすい。結論を先に書くと、**IT・Web業界の採用代行は、母集団形成・一次対応・日程調整・記録は外に出せる一方、要件の決定・技術の見極め・条件の判断は社内に残さないと採れません。**代行に出す前に、三つの難しさを自社の状況で分解し、工程ごとに「任せる・残す」を決めることが、代行が機能する条件です。職種ごとの切り分けは[エンジニア採用を代行に出す判断基準](/media/rpo-engineer-rpo/)や[SRE採用を代行に出す判断基準](/media/rpo-sre-rpo/)に書いています。ここでは、業界全体で共通する切り分けに絞ります。

## IT・Web業界の採用が難しい三つの理由

| 難しさ | 中身 | 代行への影響 |
|---|---|---|
| 職種が細かく分かれている | エンジニアの中でも、バックエンド・フロントエンド・インフラ・SRE・データ、さらにPdMやデザイナー。同じ「エンジニア」でも要件が違う | 職種ごとに要件と検索と文面が要る。「エンジニア採用の経験」だけでは足りない |
| 候補者が複数の会社を同時に見ている | スカウトが多く届き、選考が並行する。返事が遅い会社は選ばれない | 日程調整と返事の速さが、そのまま結果になる |
| 技術の見極めを社外に出しにくい | 経歴の言葉だけでは技術の深さが読めず、社内の技術者が見る必要がある | 代行に「見極め」を任せると、ずれた候補者が面接に来る |

三つのうち、代行で解決できるのは二つ目（速さ）で、一つ目と三つ目は社内の関わりが要ります。ここを分けずに「全部任せる」と、応募は増えても採用は決まりません。

## 工程ごとの「任せられる・残す」

| 工程 | 任せられるか | 理由 |
|---|---|---|
| 採用要件の決定 | 残す | 職種ごとの技術の要件は、社内の技術者が決める。代行は「経歴で読める言葉」に整えるまで |
| 母集団形成（媒体・スカウト） | 任せられる | 検索条件と文面の型があれば、外で回せる。ただし対象の層は社内が決める |
| スカウトの一次対応（返信・日程） | 任せられる | 速さが要る工程。外に出すと即日で返せる |
| 書類の一次確認 | 一部任せられる | 必須の照合（経歴で読めるもの）は外で。技術の深さは社内で |
| 技術の見極め（面接、課題） | 残す | 社内の技術者が行う。代行は面接の設計と記録の形まで |
| 条件の判断 | 残す | 年収の幅、働き方は会社の判断 |
| 内定後の接点 | 一部任せられる | 接点の設計と連絡の型は外で。迷いへの答えは社内の人が |
| 記録と報告 | 任せられる | 一覧と週次の一枚 |

「残す」と書いた工程に社内の人がいない場合、代行に出しても採れません。まず社内に「要件を決める人」「技術を見る人」「条件を決める人」がいるかを確かめます。

### エラベルの見解

多くの会社が見落とすのは、「技術の見極めを残す」の前に、「要件を経歴で読める言葉にする」が必要な点です。社内の技術者が「モダンな技術スタックに慣れている人」「設計ができる人」と要件を言い、代行がそのまま検索すると、対象が絞れず、面接に来る人がずれます。「〇〇の構成を、設計から運用まで一人で担った経験」「〇〇の規模のトラフィックで、障害の対応を自分で行った経験」のように、担った仕事の中身の言葉に直すことが、代行が機能する前提です。エラベルで担当者を選ぶ企業には、「要件を、経歴で読める言葉に直す作業を、誰と行いますか」を、私たちから先に聞いています。この作業を代行の担当者と社内の技術者が一緒に行う形にできるかが、最初の分かれ目です。要件の整理の型は[エンジニアの採用要件の作り方](/media/rpo-engineer-youken/)に書いています。

## 代行に出す前に社内で確認すること

| 確認 | 中身 |
|---|---|
| 職種ごとに要件を決める人がいるか | エンジニアの職種ごとに、社内の技術者が要件を言葉にできるか |
| 技術を見る人の時間があるか | 面接の枠を週に何枠出せるか。出せなければ、母集団を増やしても面接で詰まる |
| 条件の幅を先に出せるか | 年収の幅、働き方を、スカウトの段階で伝えられるか。伝えられないと候補者が面談前に離れる |
| 返事の速さの体制 | 候補者からの返信に、翌営業日中に返せる窓口があるか |
| 記録の形 | 候補者の一覧と面接の記録が、社内の環境にあるか。無ければ代行と一緒に作る |

五つのうち、「技術を見る人の時間」が最も詰まります。代行で応募が増えても、面接の枠が無ければ、候補者は他社に流れます。速さの構造は[日程調整が遅くて候補者が流れる](/media/rpo-nittei-chousei-osoi/)に書いています。

## 職種ごとに代行の型が違う

| 職種 | 代行に向く工程 | 社内に残す度合い |
|---|---|---|
| バックエンド・フロントエンド | 母集団形成、一次対応 | 技術の見極めは社内。要件は職種ごと |
| インフラ・SRE | 母集団形成（対象が少なく、スカウト中心） | 要件の言葉が特に具体である必要 |
| データ | 母集団形成、一次対応 | 課題の設計は社内 |
| PdM・PjM | 母集団形成、カジュアル面談の設計 | 経歴で読めない部分が多く、面談の設計が要る |
| デザイナー | 母集団形成、ポートフォリオの一次確認 | 評価は社内 |

「IT・Web業界の採用に強い代行」でも、職種ごとの型を持っているかは別です。職種ごとの切り分けは、[インフラエンジニア採用を代行に出す判断基準](/media/rpo-infra-engineer-rpo/)、[プロダクトマネージャー採用を代行に出す判断基準](/media/rpo-pdm-rpo/)、[デザイナー採用を代行に出す判断基準](/media/rpo-designer-rpo/)に書いています。

## 代行を選ぶときの確認項目

| 確認 | 聞き方 |
|---|---|
| 職種ごとの型があるか | 「バックエンドとSREで、検索条件と文面をどう変えますか」 |
| 担当者の経歴 | 「担当する方は、IT・Web業界のどの職種の採用を、どの工程で担った経験がありますか」 |
| 要件の整理を一緒に行うか | 「要件を経歴で読める言葉に直す作業を、社内の技術者とどう行いますか」 |
| 返事の速さ | 「候補者からの返信に、何営業日以内に返しますか。日程の確定は」 |
| 記録の置き場所 | 「候補者の一覧と記録は、どこに置きますか。契約が終わったら」 |
| 費用の構造 | 「月額の範囲に含まれる工程と、含まれない工程はどれですか」 |

費用は、月額型・成果報酬型・時間単価型で構造が違い、含まれる工程で変わります。金額の相場を先に聞くより、「同じ工程を任せた場合」で比べる軸をそろえます。費用の構造は[採用代行の費用の内訳](/media/rpo-hiyou-uchiwake/)に、選び方の軸は[採用代行会社の選び方](/media/rpo-erabikata/)に書いています。

## 代行に出したあとに起きること

| 起きること | 原因 | 対応 |
|---|---|---|
| 応募は増えたが、面接に来る人がずれている | 要件が経歴で読める言葉になっていない | 要件を社内の技術者と直す |
| 返信が来るが、面接の枠が無い | 技術を見る人の時間が確保されていない | 枠を先に預ける。段を減らす |
| 面接で「思っていた人と違う」 | 書類の一次確認で技術の深さを代行が判断した | 一次確認は必須の照合だけに。深さは社内 |
| 内定を出しても辞退される | 条件の幅を先に出していない。迷いに答えていない | 幅を先に。内定後の接点を社内の人が |
| 契約が終わると記録が消える | 記録が代行の環境にある | 社内の環境に置く形を契約で |

出したあとの問題の多くは、「残す工程を残していない」か「記録の置き場所」に戻ります。契約の前に、工程の切り分けと記録の置き場所を書面にします。

### エラベルの見解

相談で多いのは、「代行を使ったが、うまくいかなかった」という経験を持つ会社からの問い合わせです。聞くと、代行の担当者に「エンジニア採用の経験がある」と説明されたが、実際にはSIerの営業職の採用が主で、IT・Web業界の職種ごとの型を持っていなかった、という話が続きます。IT・Web業界では、「エンジニア採用の経験」を職種と工程まで分けて確かめることが、他の業界より重要です。エラベルは、担当者の経歴を、職種と担った工程で見てから決められる形にしています。「バックエンドの母集団形成を担った」「SREのスカウト文面を作った」「PdMのカジュアル面談を設計した」のように、職種と工程の組み合わせで確かめると、自社の残す工程と任せる工程に合う担当者かが分かります。合わない担当者に全部を任せるより、合う担当者に一つの工程を任せるほうが、結果は出ます。

## まとめ

- IT・Web業界の採用の難しさは、**職種の細かさ・候補者の並行・技術の見極め**の三つ。代行で解決できるのは速さだけ
- **母集団形成・一次対応・日程・記録は任せられ、要件・技術の見極め・条件は残す**
- 代行に出す前に、**要件を決める人・技術を見る人の時間・条件の幅・返事の体制・記録の形**を社内で確かめる
- 職種ごとに代行の型が違う。**「エンジニア採用の経験」を職種と工程で確かめる**
- 費用は**同じ工程で比べる軸**をそろえる。相場を先に聞かない
- 出したあとの問題は、**残す工程を残していないか、記録の置き場所**に戻る

## よくある質問

### 社内に技術者が一人しかおらず、面接の時間が取れません

一人の技術者の面接の枠を、週に一枠でも先に確保し、その枠に合う人数だけを母集団形成の目標にします。枠を超えて応募を増やしても、面接で詰まり、候補者が流れます。技術の見極めを一次と二次に分け、一次を「経歴で読める必須の照合」（代行）、二次を「技術者との面接」（社内）にすると、技術者の時間を最終の候補者だけに使えます。技術者がいない場合の組み方は[エンジニア採用を代行に出す判断基準](/media/rpo-engineer-rpo/)に書いています。

### スタートアップで、採用の体制も記録も無い状態です

体制と記録が無い状態で代行に全部を任せると、契約が終わった時点で何も残りません。最初に「候補者の一覧」と「面接の記録の形」を社内の環境に置き、代行がそこに書き込む形にします。要件を決める人と条件を決める人は、経営者が担うことが多く、その時間を先に確保します。スタートアップに向く代行の条件は[スタートアップに向く採用代行の条件](/media/rpo-startup-muke/)に、急成長の段階の体制は[急成長フェーズの会社の採用体制の作り方](/media/rpo-kyuu-seichou-taisei/)に書いています。

### 代行に「技術の見極めもできる」と言われました。任せてよいですか

担当者が元エンジニアでも、自社の技術の要件と、自社のチームで一緒に働けるかは、社内の技術者にしか判断できません。代行に任せられるのは、「経歴で読める必須の照合」と「面接の設計（観点・記録の形）」までです。技術の深さの判断を代行に任せると、面接に来る人がずれ、社内の技術者の時間が無駄になります。「見極めもできる」と言う代行には、「見極めの結果を、社内の誰がどう確かめるか」を先に決めてから任せます。
