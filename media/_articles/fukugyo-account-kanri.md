副業を始めて数件を回すうちに、媒体のアカウント、依頼側のATS、チャット、クラウドの共有と、アカウントが増えた。どれが今の案件のもので、どれが終わった案件のものかが分からなくなり、終わった依頼側の仕組みにまだ入れる状態のものもある。結論を先に書くと、**副業のアカウントは、「自分が作ったもの」「依頼側から発行されたもの」「依頼側と共有しているもの」の三種類に分けて一覧にし、案件の開始時に足し、終了時に消すか停止を確認します。最も危ないのは、終わった案件のアカウントが放置され、まだ入れる状態で残っていることです。**一覧があれば、増減を見るだけで放置が無くなります。パスワードの受け取り方は[パスワードの受け渡し](/media/fukugyo-password/)に、端末とアカウントの分け方は[情報の取り扱いと端末の分離](/media/fukugyo-security/)に、案件ごとの情報の分け方は[使うツールをそろえる](/media/fukugyo-tool/)にまとめています。技術的な設定は、依頼側の情報管理の担当者に確認してください。

## アカウントが増えて起きる問題

アカウントが増えること自体は避けられません。管理せずに増やすと、次の問題が起きます。

| 問題 | 何が起きるか |
|---|---|
| 終わった案件のアカウントが残る | 依頼側の仕組みにまだ入れる。依頼側から見れば、契約の無い外部の人が情報に触れられる状態 |
| どの案件のものか分からない | 通知が来ても、どの依頼側の何の仕組みか分からず、対応が遅れる |
| パスワードの使い回し | 覚えられない数になり、同じパスワードを使い始める。一つ漏れると全部に広がる |
| 依頼側の情報が自分のクラウドに残る | 共有のフォルダやチャットに残った依頼側の資料が、案件の後も自分の側に同期されている |
| 本業のアカウントと混ざる | 副業の仕組みに本業のアカウントでログインしてしまう。本業の管理下に依頼側の情報が入る |
| 多要素認証の設定が残る | 終わった依頼側の仕組みの認証の通知が、スマートフォンに来続ける |

問題の要点は、「終わった案件のアカウントが残る」ことです。契約中のアカウントは、使っているので管理の目が届きますが、終わった案件のものは、使わないので忘れます。忘れたアカウントが、依頼側から見て「まだ入れる外部の人」として残り、後で情報の問題が起きたときに疑われる対象になります。外部の立場で疑われやすい構造は[パスワードの受け渡し](/media/fukugyo-password/)にも書いています。

## 三種類に分ける理由

アカウントを一つの一覧にするとき、種類で分けておくと、開始時と終了時にやることが変わります。

| 種類 | 例 | 誰が管理するか | 終了時にやること |
|---|---|---|---|
| 自分が作ったもの | 副業用のメール、副業用のクラウド、媒体に自分で登録したアカウント、パスワード管理のツール | 自分 | 残す。依頼側の情報が入っていれば消す |
| 依頼側から発行されたもの | 依頼側のATS、依頼側が契約する媒体の自分専用のID、依頼側のチャットの招待、依頼側の社内の共有 | 依頼側 | 依頼側に停止を依頼し、停止の連絡をもらう。自分では消せない |
| 依頼側と共有しているもの | 社内で使い回している媒体のID、共有のメールアドレス、共有のフォルダ | 依頼側だが、自分もパスワードを知っている | 依頼側にパスワードの変更を依頼し、変更の連絡をもらう |

分ける要点は、「誰が管理していて、終了時に誰が動くか」が種類で違うことです。自分が作ったものは自分で消せますが、依頼側から発行されたものは依頼側にしか止められず、共有のものは依頼側が変えないと自分の知識が残ります。一覧に種類を書いておけば、終了時に「依頼側に頼むこと」と「自分でやること」がすぐ分かります。

### エラベルの見解

相談で最も多い思い込みは、「案件が終われば、依頼側がアカウントを止めてくれる」というものです。実際には、依頼側の採用の担当者は、外部の担当者のアカウントの停止を情報管理の担当者に依頼する手順を知らないか、忘れることが多く、止まらないまま残っている例が珍しくありません。残っていることに気づくのは、次に情報の問題が起きたときで、そのときに「まだ入れる状態だった外部の人」として名前が挙がります。

見ていて差がつくのは、終了時に自分から「私のアカウントの停止をお願いします」と文面で伝え、停止の連絡をもらって記録に残しているかです。これをしている人は、後で問題が起きても「〇日に停止を依頼し、〇日に停止の連絡を受けた」と示せます。エラベルでは、案件の終了時に、依頼側に担当者のアカウントの停止を依頼する形を取っていますが、担当者自身も一覧を持って確認していると、依頼側の側で漏れがあっても気づけます。アカウントは、作るときより、終わるときの扱いで差が出ます。

## 一覧に残す項目

一覧は、表計算の一枚で足ります。パスワードは一覧に書かず、パスワード管理のツールに置きます。

| 項目 | 内容 | 要点 |
|---|---|---|
| 案件 | どの依頼側の案件か | 案件が終わったら、行を消さずに「終了」の印を付ける |
| 仕組みの名前 | 媒体、ATS、チャット、クラウドなど | 依頼側が使っている名前で |
| 種類 | 自分・発行・共有 | 終了時の手順がこれで決まる |
| ID | ログインに使うIDかメールアドレス | パスワードは書かない |
| 発行日 | いつ受け取ったか | 契約の開始と合っているか |
| 権限 | 何ができる権限か | 必要以上に広ければ依頼側に伝える |
| 多要素認証 | 有効か。確認用の端末は何か | 終了時に端末側の設定を消す |
| 停止・変更の予定 | 契約の終了日 | 終了時に依頼側に依頼する日 |
| 停止・変更の確認 | 依頼側から停止や変更の連絡をもらった日 | 空欄が残っていれば、放置されている |

項目の要点は、「停止・変更の確認」の列です。終了した案件の行で、この列が空欄なら、まだ止まっていないか、止まったことを確認していないかのどちらかです。月に一度、この列の空欄を探すだけで、放置が見つかります。パスワードを一覧に書かない理由は、一覧が漏れたときに全部が使える状態になるからで、パスワード管理のツールと分けます。ツールの分け方は[使うツールをそろえる](/media/fukugyo-tool/)に整理しています。

## 案件の開始時と終了時の手順

一覧は、案件の開始時と終了時に更新します。この二つの時点で漏れなければ、途中で崩れません。

| 時点 | 手順 |
|---|---|
| 開始時 | 一、依頼側から発行されるアカウントの一覧を担当者に聞く。二、専用のアカウントの発行を頼む。三、受け取ったらパスワードを変え、多要素認証を有効にし、権限を見る。四、一覧に行を足す。五、自分が作る副業用のアカウント（案件用のフォルダなど）も足す |
| 途中 | 依頼側が新しい仕組みを入れたとき、担当者が替わって発行し直したときに、行を足すか直す |
| 終了時 | 一、一覧からその案件の行を全部見る。二、種類ごとに、自分で消す・停止を依頼する・変更を依頼する、を分ける。三、依頼側に文面で依頼する。四、依頼側から連絡が来たら確認の列に日付を入れる。五、自分の端末の多要素認証の設定とブラウザの保存情報を消す。六、行に「終了」の印を付ける |

手順の要点は、終了時の「三」の文面で依頼することです。口頭で「止めておいてください」と言うと、依頼側の担当者は忘れます。「私に発行いただいた〇〇と〇〇のアカウントを、〇日以降停止してください。共有の〇〇はパスワードの変更をお願いします」と文面で送れば、担当者はそれを情報管理の担当者に転送でき、自分の側にも記録が残ります。終了時の全体の手順は[引き継ぎの進め方](/media/fukugyo-hikitsugi/)に、端末側の整理は[私物端末で作業してよいか](/media/fukugyo-tanmatsu/)に書いています。

## 自分のアカウントの整え方

自分で作るアカウントは、案件ごとに増やさず、副業用の一組を使い回します。

| アカウント | 整え方 |
|---|---|
| 副業用のメール | 一つ。案件ごとに作らない。依頼側との連絡、媒体の登録、請求の送付をすべてここで |
| 副業用のクラウド | 一つ。中を案件ごとのフォルダで分ける。依頼側の情報を置くなら、案件の終了時にそのフォルダを消す |
| パスワード管理のツール | 一つ。副業用の利用者で使う。本業の会社のツールには入れない |
| 媒体に自分で登録したアカウント | 依頼側の契約する媒体に、自分で登録することは通常無い。依頼側から発行されるものを使う。自分で登録したものがあれば、それは「自分」の種類 |
| SNSや発信のアカウント | 副業の案件とは分ける。依頼側の仕組みへのログインに使わない |
| 本業のアカウント | 副業の仕組みに一切使わない。ログインの選択で本業のアカウントが出てきたら、選ばない |

整え方の要点は、「副業用の一組を使い回し、案件ごとに増やさない」ことです。案件ごとにメールやクラウドを作ると、一覧が増え、終了時に消す作業も増えます。副業用の一組の中で、案件ごとにフォルダやラベルで分ければ、一覧に載るのは依頼側から発行されたものが中心になり、管理が軽くなります。本業のアカウントとの分離は[情報の取り扱いと端末の分離](/media/fukugyo-security/)に、ログインの誤りが起きやすい場面は[ネットワーク環境の注意](/media/fukugyo-vpn/)に書いています。

## 依頼側から発行されたアカウントの扱い

依頼側から発行されたアカウントは、依頼側のものを借りている状態なので、自分のものとは扱いが違います。

| 扱い | 内容 |
|---|---|
| 設定を勝手に変えない | 通知の設定や表示の設定は変えてよいことが多いが、権限や共有の範囲に関わる設定は依頼側に確認する |
| 他の人に貸さない | 家族にも、副業の仲間にも、依頼側の別の担当者にも。自分の名前で記録が残る |
| 依頼側の情報を外に出さない | 依頼側の仕組みからダウンロードした情報を、自分のクラウドに置かない。置く必要があるなら依頼側に確認する |
| 権限の範囲で使う | 見える情報でも、自分の範囲外のもの（他の職種の候補者、給与の情報など）は見ない。見えること自体を依頼側に伝えて、権限を絞ってもらう |
| 異常があれば伝える | 自分のアカウントで身に覚えの無い操作の記録があった、ログインの通知が来た、などは、すぐ依頼側に伝える |
| 契約が終わったら使わない | 停止されていなくても、契約の終了後にログインしない。「まだ入れた」は、入ったことになる |

扱いの要点は、「契約が終わったら使わない」ことです。依頼側が停止を忘れていて、まだログインできる状態でも、契約の終了後に入ることは、依頼側から見れば無断で情報に触れたことになります。停止の依頼をして、連絡を待ち、入らない。もし「停止されていないようです」と気づいたら、それを依頼側に伝えます。権限の範囲の考え方は[権限がないと動けない場面](/media/fukugyo-kengen-nai/)に整理しています。

## 放置を防ぐ定期の見直し

一覧があっても、見直さなければ放置は起きます。見直しの時期を決めておきます。

| 時期 | 見ること |
|---|---|
| 月に一度 | 「停止・変更の確認」の列に空欄が無いか。終了した案件の行で、確認が取れていないものは依頼側に再度依頼する |
| 契約の更新のとき | その案件のアカウントの権限が、更新後の範囲と合っているか。範囲が変わったなら権限も見直す。[更新時の条件見直し](/media/fukugyo-keiyaku-koushin-koushou/) |
| 依頼側の担当者が替わったとき | 新任の担当者に、自分のアカウントの一覧を伝える。前任が発行したものを新任が把握していないことがある |
| 端末を替えたとき | 多要素認証の確認用の端末を替える。古い端末に残った設定を消す |
| 数か月に一度 | 使っていないアカウントが無いか。自分が作ったもので、案件が終わって不要なものは消す |
| 年に一度 | パスワードの使い回しが無いか。パスワード管理のツールの中を見る |

見直しの要点は、「月に一度、確認の列の空欄を探す」ことです。これだけで、終了した案件のアカウントの放置はほぼ無くなります。他の見直しは、それぞれの時点で一覧を開く習慣があれば、自然にできます。稼働ログや請求の記録と同じ日に見直すと、忘れません。記録の習慣は[稼働ログの付け方](/media/fukugyo-log/)に書いています。

### エラベルの見解

担当する側から見ると、アカウントの一覧を持っている人と持っていない人の差は、案件が三件を超えたあたりで出てきます。一件や二件のうちは、記憶で管理できます。三件を超え、終わった案件が混ざり始めると、記憶では追えず、「あの依頼側のATSはまだ入れるのか」が分からなくなります。一覧を持っている人は、案件が増えても、開始と終了で行を足し引きするだけで、状態が常に分かっています。

順番として、最初の一件のときに一覧を作る。一件しか無くても、行が一つある一覧を作っておけば、二件目からは足すだけになります。三件目になってから作ろうとすると、過去の分を思い出して書くことになり、抜けが出ます。エラベルでは、案件の開始時に依頼側から発行されるアカウントを担当者に伝え、終了時に停止を依頼側に依頼していますが、担当者自身が一覧を持っていると、依頼側の側の漏れにも気づけます。アカウントの一覧は、情報の扱いで信頼される担当者の、最も簡単な道具です。

## まとめ

- アカウントは**自分が作ったもの・依頼側から発行されたもの・依頼側と共有しているもの**の三種類に分けて一覧にする
- 最も危ないのは**終わった案件のアカウントの放置**。依頼側が止めてくれるとは限らない
- 一覧には**案件・仕組み・種類・ID・発行日・権限・多要素認証・停止の予定・停止の確認**を書き、パスワードは書かない
- 開始時に**専用の発行を頼み・変えて・権限を見て・行を足す**。終了時に**種類ごとに分けて・文面で依頼し・確認を記録し・端末側を消す**
- 自分のアカウントは**副業用の一組を使い回し、案件ごとに増やさない**。本業のアカウントは一切使わない
- 発行されたものは**設定を変えず・貸さず・情報を外に出さず・権限の範囲で使い・契約が終わったら入らない**
- **月に一度、確認の列の空欄を探す**。更新・担当者の交代・端末の交換でも見直す

## よくある質問

### 終わった案件のATSに、まだログインできることに気づきました

ログインせずに、依頼側に「私のアカウントがまだ有効のようです。停止をお願いします」と文面で伝えます。気づいた経緯を聞かれたら、「ログインの通知が来た」「一覧の確認で停止の連絡が無いことに気づいた」など、事実を伝えます。「試しに入ってみたら入れた」は、契約の終了後に情報に触れたことになるので、確認のためでも入りません。停止の連絡が来たら、一覧の確認の列に日付を入れます。

### 依頼側から、社内の人と同じ権限の広いアカウントを発行されました

自分の範囲に不要な権限（候補者の削除、設定の変更、他の職種の情報、請求の情報など）があれば、「この権限は私の業務には不要なので、外していただけますか」と伝えます。広い権限は便利なようで、問題が起きたときに疑われる範囲を広げます。依頼側の仕組みの都合で権限を絞れない場合は、「見えるが触らない範囲」を文面で依頼側と確認し、一覧の権限の列に書いておきます。

### パスワード管理のツールに、依頼側から発行されたアカウントの情報を入れてよいですか

自分専用に発行されたアカウントのパスワードは、自分が管理するものなので、副業用のパスワード管理のツールに入れて構いません。ただし、本業の会社が提供するツールには入れず、副業用の利用者で使うツールに入れます。共有のアカウントのパスワードも同様ですが、案件の終了時に依頼側が変更したら、自分のツールからは消します。依頼側がパスワードの保管の方法を指定している場合は、それに従います。
